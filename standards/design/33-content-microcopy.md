Research completed with Firecrawl first. The specification below treats content as part of the product contract: terminology, microcopy, onboarding, validation, support, localisation, and content operations MUST be designed and governed with the same rigor as components and data semantics.

# Content, Microcopy, Help & Onboarding — Gold Standard 2026

**Canonical placement:** Content Standards → **Content, Microcopy, Help & Onboarding** → Forms & Validation → Components → Patterns  
**Status:** Normative  
**Component baseline:** shadcn/ui + Radix/native semantics  
**Accessibility target:** WCAG 2.2 AA or higher  
**Primary domain:** environmental, geospatial, forestry, land-cover, remote-sensing, scientific and enterprise data products  
**Applies to:** UI strings, documentation, forms, dashboards, maps, notifications, onboarding, help, support, emails generated by the product, empty states, errors, changelogs, upgrade surfaces, status messaging, and localisation source strings.

---

# 1. Purpose

Content is part of the interface.

It determines whether users understand:

```text
what happened
what something means
what they can do
what they should do next
what the system knows
what the system does not know
```

Content MUST therefore be designed alongside:

- interaction;
- navigation;
- forms;
- state;
- permissions;
- data semantics;
- accessibility;
- localisation.

It MUST NOT be treated as placeholder text added after implementation.

GOV.UK defines content design as starting with user needs and designing clear, accessible content that helps people find information or complete a task.  
https://www.gov.uk/guidance/content-design/what-is-content-design

Apple similarly treats language as a core part of the interface, recommends establishing a consistent voice, varying tone by context, using plain language, and writing with accessibility and localisation in mind.  
https://developer.apple.com/design/human-interface-guidelines/writing

The governing sequence is:

```text
user need
↓
information required
↓
content hierarchy
↓
language
↓
interaction
↓
component
↓
localisation
↓
measurement
```

Not:

```text
component built
↓
empty string
↓
someone writes copy later
```

# 2. Rules

# 2.1 Voice and tone

**Voice** is the organisation's stable personality.

**Tone** changes according to the user's situation.

Apple explicitly distinguishes a consistent product voice from contextual tone changes.  
https://developer.apple.com/design/human-interface-guidelines/writing

The environmental/geospatial product voice MUST be:

```text
precise
calm
evidence-led
plain-spoken
transparent
respectful
operational
```

It SHOULD feel like a competent analyst or field specialist explaining the system clearly.

It MUST NOT sound like:

```text
an advertising agency
a sustainability campaign slogan
a chatbot pretending to be a friend
a sci-fi command centre
a legal department unless the content is legal
```

---

# 2.2 Voice attributes

## Precise

State what is known.

Good:

```text
3.8 ha of probable canopy loss detected
```

Avoid:

```text
Major deforestation event detected
```

unless the system has sufficient evidence to classify the event as deforestation.

---

## Evidence-led

Content MUST distinguish:

```text
observation
model output
inference
verification
policy conclusion
```

Example:

```text
Satellite detection
Field verification pending
```

is materially different from:

```text
Confirmed illegal clearing
```

The product MUST NOT collapse those states through dramatic wording.

---

## Calm

Routine system conditions MUST use neutral language.

Good:

```text
Upload failed
```

Avoid:

```text
Oops! Something went terribly wrong!
```

Errors are already disruptive.

Copy SHOULD reduce uncertainty rather than add emotional noise.

---

## Transparent

Where relevant, explain:

- source;
- freshness;
- confidence;
- limitation;
- scope.

Good:

```text
Model confidence: 82%
Imagery acquired 18 Sep 2026
```

Avoid:

```text
Highly accurate detection
```

unless "highly accurate" has a governed definition.

---

## Operational

Write toward decisions and next steps.

Prefer:

```text
Review 12 new detections
```

over:

```text
Explore the latest insights
```

# 2.3 Tone matrix

| Context | Tone | MUST do | MUST NOT do |
|---|---|---|---|
| Normal | Neutral, concise | State task/content | Add personality for its own sake |
| Success | Calm, affirmative | Confirm outcome | Celebrate routine saves excessively |
| Warning | Direct, measured | Explain risk and consequence | Alarm unnecessarily |
| Error | Specific, constructive | Explain problem + recovery | Blame user |
| Empty | Helpful, contextual | Explain why + next step | Use jokes as substitute for guidance |
| Destructive | Serious, explicit | Name object + consequence | Use vague buttons |
| Permission | Respectful, factual | Explain access condition where allowed | Imply system malfunction |
| Legal/compliance | Formal, exact | Preserve approved wording | Rewrite for personality |
| Safety/environmental risk | Cautious, evidence-led | State uncertainty/status | Sensationalise |
| Billing/paywall | Transparent | State limit, value, consequence | Shame or pressure |
| Loading | Quiet | Indicate operation/status where useful | Invent progress |

---

# 2.4 Success tone

Routine success SHOULD be understated.

Good:

```text
Changes saved
```

or:

```text
Dataset uploaded
```

Avoid:

```text
Amazing! Your dataset has been successfully uploaded! 🎉
```

Celebratory tone MAY be appropriate for meaningful milestones.

Example:

```text
Workspace setup complete
```

A successful save is not generally a milestone.

---

# 2.5 Error tone

Error content MUST be:

```text
specific
blameless
actionable
```

W3C recommends clear, understandable instructions and error messages and avoiding unnecessary technical language.  
https://www.w3.org/WAI/tips/writing/

GOV.UK validation guidance requires users to be told what went wrong and how to fix it, and recommends preserving their entered information when validation fails.  
https://design-system.service.gov.uk/patterns/validation/

Do NOT write:

```text
Invalid input
```

when the product can write:

```text
Enter an area between 0.1 and 10,000 ha
```

---

# 2.6 Empty-state tone

Empty states SHOULD be factual and useful.

Apple recommends that empty states explain what users can do next and provide an action where possible.  
https://developer.apple.com/design/human-interface-guidelines/writing

Carbon similarly recommends explaining why data is absent and providing a corrective or next action where one exists.  
https://carbondesignsystem.com/patterns/empty-states-pattern/

Good:

```text
No detections yet

Detections will appear after imagery for this area
has been processed.

[View processing schedule]
```

Avoid:

```text
Nothing here yet 🌱
Good things are growing!
```

when the user needs operational information.

---

# 2.7 Destructive tone

Destructive content MUST be explicit about:

```text
what will be affected
whether the action is reversible
what associated data is affected
```

Example:

```text
Delete saved view?

"Weekly protected-area review" will be permanently deleted.
This does not delete the underlying detections.

[Cancel]
[Delete saved view]
```

Do NOT use:

```text
Are you sure?

[No]
[Yes]
```

Apple recommends specific alert actions rather than ambiguous `Yes` / `No` labels.  
https://developer.apple.com/design/human-interface-guidelines/writing

---

# 2.8 Legal tone

Legal, regulatory, privacy, licence, and statutory content MAY intentionally differ from ordinary product voice.

Approved legal text MUST NOT be casually shortened.

However, supporting explanation MAY be written in plain language.

Canonical pattern:

```text
Plain-language explanation
↓
required legal wording
↓
link to full policy
```

Do NOT reinterpret legal obligations through friendly microcopy.

---

# 2.9 Environmental and geospatial terminology

The product MUST use scientifically and operationally defensible language.

Terms MUST reflect the actual analytical state.

Examples:

| Prefer | Avoid / forbidden without evidence |
|---|---|
| detected change | destruction |
| probable canopy loss | confirmed deforestation |
| model confidence | accuracy, unless actually accuracy |
| imagery acquired | live satellite |
| protected-area overlap | protected-area violation |
| field verification pending | unverified illegal activity |
| estimated area | exact area |
| land-cover class | land use, unless actual use |
| observation | truth |
| no observation | no change |
| cloud obscured | clear / zero |
| classification | identification, when only class inference |
| anomaly | incident, unless incident confirmed |
| reference period | before |
| comparison period | after |
| dataset | database, unless technically a database |
| map layer | map, when referring to one layer |
| geographic coordinates | location code |
| longitude / latitude | X / Y, unless context explicitly uses projected coordinates |

---

# 2.10 Domain glossary

A product glossary MUST define specialised vocabulary users need to understand.

Canonical entries SHOULD include:

| Term | Preferred definition |
|---|---|
| Canopy loss | Reduction in detected tree-canopy cover according to the stated methodology |
| Land cover | Physical material or vegetation covering the Earth's surface |
| Land use | How people use or manage land |
| Detection | A system-generated observation meeting defined criteria |
| Verification | Human or authoritative confirmation of an observation |
| Confidence | Model-specific measure expressing confidence in a result; not automatically equivalent to accuracy |
| Baseline | Reference dataset or period used for comparison |
| Acquisition date | Date imagery or sensor data was captured |
| Processing date | Date data was analysed or generated |
| Resolution | Spatial or temporal granularity of the source data |
| Protected area | Geographically defined area with a governed protection status |
| Layer | One visual/data dataset rendered in a map |
| Feature | A geographic object represented in a map dataset |
| Raster | Grid-based spatial data |
| Vector | Point, line, or polygon spatial data |
| CRS | Coordinate reference system used to represent geographic coordinates |

Technical glossary terms SHOULD be linked where the user encounters them in documentation.

W3C explicitly recommends expanding unfamiliar acronyms and considering a glossary for terms readers may not know.  
https://www.w3.org/WAI/tips/writing/

# 2.11 Forbidden terminology

The following MUST NOT appear in production content unless intentionally quoting another source:

```text
magic
revolutionary
game-changing
effortless
frictionless
seamless
world-class
best-in-class
next-generation
cutting-edge
supercharge
unlock
unleash
transformative
powerful insights
actionable insights
at your fingertips
single pane of glass
```

These phrases MAY be meaningful in rare context, but SHOULD be presumed banned until specifically justified.

---

# 2.12 UI and documentation terminology

A feature MUST use the same canonical noun across:

```text
UI
documentation
support
release notes
API-facing documentation where appropriate
training
```

If the UI says:

```text
Saved views
```

documentation MUST NOT call the same feature:

```text
Presets
```

unless the distinction is intentional.

Documentation MAY include synonyms for searchability.

The visible product terminology remains canonical.

---

# 2.13 Headings

Headings MUST describe the content or task beneath them.

W3C recommends short headings that group related content and form a meaningful outline.  
https://www.w3.org/WAI/tips/writing/

Prefer:

```text
Review canopy-loss detections
```

over:

```text
Overview
```

when the former communicates the actual task.

Prefer:

```text
Unable to load satellite imagery
```

over:

```text
Error
```

---

# 2.14 Heading hierarchy

Page headings SHOULD answer:

```text
What am I looking at?
```

Section headings SHOULD answer:

```text
What information is in this section?
```

Avoid headings that only describe layout:

```text
Section 1
Details
Information
More
```

unless those labels genuinely match the domain.

---

# 2.15 Sentence-style capitalization

UI labels and headings SHOULD use sentence-style capitalization unless the brand or language convention explicitly requires otherwise.

Material Design recommends sentence-style capitalization throughout titles, headings, navigation, labels, menu items, and buttons.  
https://m3.material.io/foundations/content-design/style-guide

Prefer:

```text
Create monitoring area
```

not:

```text
Create Monitoring Area
```

---

# 2.16 Button labels

Button labels MUST describe the action.

The preferred model is:

```text
verb + object
```

Examples:

```text
Create project
Save changes
Upload dataset
Export CSV
Delete layer
Review detections
Add member
```

Object MAY be omitted where context makes it unambiguous:

```text
Save
Continue
Cancel
```

A button MUST NOT say:

```text
Submit
Proceed
OK
Yes
No
Click here
```

when a more precise action is available.

---

# 2.17 Primary action labels

The primary action label MUST describe the immediate result, not an abstract workflow step.

Prefer:

```text
Send invitation
```

over:

```text
Continue
```

if clicking the button actually sends the invitation.

`Continue` is appropriate when it only advances to the next step and does not commit the task.

---

# 2.18 Field labels

Field labels MUST be persistent.

Placeholder text MUST NOT substitute for labels.

Good:

```text
Monitoring area name
[_________________]

Used in maps, reports and exports
```

Avoid:

```text
[Enter monitoring area name...]
```

with no visible label.

---

# 2.19 Field labels vs questions

Use concise noun labels for familiar structured data.

Example:

```text
Dataset name
```

Use full questions when the user must make a meaningful decision.

Example:

```text
How should detections be prioritised?
```

The form standard remains authoritative for question-page composition.

---

# 2.20 Help text

Help text SHOULD explain information users need **before** entering data.

Use help text for:

- expected format;
- consequence;
- scope;
- example;
- privacy/use;
- difficult domain concept.

Example:

```text
Minimum detection area
Only detections at or above this area will appear in alerts
```

Do NOT repeat the label:

```text
Minimum detection area
Enter the minimum detection area
```

---

# 2.21 Examples

Examples SHOULD clarify input syntax.

Example:

```text
Coordinates
For example, 3.1390, 101.6869
```

Examples MUST NOT accidentally imply that only the example format/value is accepted if others are valid.

---

# 2.22 Tooltip content

Tooltips SHOULD explain:

- unfamiliar icons;
- concise concepts;
- abbreviations;
- secondary detail.

NN/g recommends tooltips for supplementary information rather than required instructions.  
https://www.nngroup.com/articles/tooltip-guidelines/

A tooltip MUST NOT contain information required to complete a critical task if no equivalent visible route exists.

Do NOT hide:

```text
why a field is required
billing consequences
dangerous-action consequences
```

inside hover-only tooltips.

---

# 2.23 Confirmation dialogs

Confirmation dialogs SHOULD be reserved for:

```text
irreversible actions
high-cost actions
unusual actions with material consequence
```

Do NOT confirm routine low-risk actions merely because implementation is asynchronous.

Canonical structure:

```text
Title:
Delete monitoring area?

Body:
"Central Pahang" and its saved configuration will be deleted.
Detection records will remain available in the archive.

Actions:
[Cancel]
[Delete monitoring area]
```

---

# 2.24 Confirmation title

The title SHOULD name the action or consequence.

Prefer:

```text
Remove 4 members?
```

over:

```text
Confirm action
```

---

# 2.25 Error-message formula

A field error SHOULD generally answer:

```text
1. What is wrong?
2. What does valid input look like?
```

Examples:

```text
Enter a monitoring area name

Area must be greater than 0 ha

Enter coordinates as latitude, longitude

End date must be after start date
```

GOV.UK explicitly recommends explaining what went wrong and how to fix it.  
https://design-system.service.gov.uk/components/error-message/

---

# 2.26 Error-message blame

Do NOT write:

```text
You entered an invalid coordinate
```

when:

```text
Enter coordinates as latitude, longitude
```

communicates the correction without blame.

Do NOT write:

```text
User error
Bad input
Illegal value
```

in end-user UI.

---

# 2.27 Error codes

Internal error codes MAY be shown as secondary support references.

Example:

```text
Imagery could not be loaded

Try again. If the problem continues, contact support.

Reference: GEO-TILE-2041
```

The error code MUST NOT replace the explanation.

---

# 2.28 System failure vs validation failure

Do not tell the user to change valid input when the service failed.

GOV.UK distinguishes user-correctable validation from system/service failures.  
https://design-system.service.gov.uk/patterns/validation/

Validation:

```text
Upload a GeoJSON file smaller than 100 MB
```

System failure:

```text
Upload service unavailable

Your file was not uploaded. Try again later.
```

---

# 2.29 Success messages

Success messages MUST confirm the completed outcome.

Good:

```text
Workspace created
```

Better when context matters:

```text
"Forest Watch Sabah" created
```

Avoid:

```text
Success!
```

as the only message.

---

# 2.30 Toasts and transient success

Routine low-risk success MAY use a toast.

Important state changes SHOULD remain visible in the page itself.

A toast MUST NOT be the only evidence that:

```text
billing changed
permission changed
data was permanently deleted
```

unless the resulting interface makes the state unmistakable.

Current shadcn/ui provides Alert, Alert Dialog, Dialog, Empty, Tooltip, and toast/notification primitives that can implement these content surfaces without creating bespoke interaction behavior.  
https://ui.shadcn.com/docs/components/base/dialog  
https://ui.shadcn.com/docs/components/base/alert-dialog  
https://ui.shadcn.com/docs/components/base/empty  
https://ui.shadcn.com/docs/components/base/tooltip

---

# 2.31 Loading messages

Loading content SHOULD identify the work only when doing so helps users.

Examples:

```text
Loading detections…
Processing imagery…
Generating export…
```

Avoid fake precision:

```text
Almost there…
99% complete
```

unless progress is known.

Indeterminate processes MUST NOT display invented percentages.

---

# 2.32 Long-running operations

For operations that may take significant time, explain:

```text
what is happening
whether the user can leave
where the result will appear
how completion is communicated
```

Example:

```text
Processing 12 imagery scenes

You can leave this page. We'll add the detections
to this project when processing finishes.
```

---

# 2.33 Destructive actions

Destructive action copy MUST identify the object.

Good:

```text
Delete dataset
```

Avoid:

```text
Delete
```

when multiple nearby objects could be affected.

If deletion is irreversible, say so.

If recoverable from trash/archive, say that instead.

---

# 2.34 Permission messaging

Permission errors MUST distinguish:

```text
resource does not exist
resource exists but user cannot access it
user lacks action permission
authentication expired
```

subject to Security disclosure requirements.

Example:

```text
You can view this project but cannot edit its monitoring rules.

Ask a workspace administrator for Editor access.
```

Do NOT say:

```text
Something went wrong
```

when the actual state is known.

Security rules determine whether the existence of a protected resource may be disclosed.

---

# 2.35 Paywall messaging

A paywall MUST explain:

```text
what is unavailable
which plan/capability provides it
what happens after upgrade
```

Good:

```text
Historical imagery export is available on the Enterprise plan

Upgrade to export imagery older than 12 months.

[Compare plans]
```

Avoid:

```text
Unlock the power of unlimited insights 🚀
```

---

# 2.36 Upgrade prompts

Upgrade prompts MUST be contextual.

They SHOULD appear when users encounter a legitimate plan boundary.

Do NOT repeatedly interrupt users who have already declined the prompt.

Do NOT obscure existing paid-for capabilities to force conversion.

---

# 2.37 Content hierarchy

Meaning MUST be front-loaded.

W3C recommends placing unique and relevant information first in page titles and using concise headings and text.  
https://www.w3.org/WAI/tips/writing/

Prefer:

```text
Upload failed: file exceeds 100 MB
```

over:

```text
We encountered an issue while attempting to complete your upload
because the selected file appears to exceed the current maximum size
```

---

# 2.38 Scan-first structure

Interfaces MUST be written for scanning.

Use:

- headings;
- short paragraphs;
- lists;
- tables;
- labels;
- meaningful links.

W3C explicitly recommends short sentences/paragraphs and list formatting where appropriate.  
https://www.w3.org/WAI/tips/writing/

Dense explanatory paragraphs SHOULD NOT appear inside routine workflows when structured content would be clearer.

---

# 2.39 Sentence length

UI sentences SHOULD be short enough to communicate one idea clearly.

There is no universal numerical sentence limit.

As a working editorial rule:

```text
one sentence
≈
one principal idea
```

Split sentences when they contain multiple conditions or actions.

Readability scores MAY identify difficult text but MUST NOT substitute for user testing or domain judgment.

---

# 2.40 Reading level

General product language SHOULD use plain language understandable without specialist training.

Technical terminology MAY be retained when it is the correct terminology for the intended expert audience.

W3C recommends simple language and avoiding unnecessary complexity; WCAG also includes a higher-level reading criterion at Level AAA for difficult text.  
https://www.w3.org/WAI/tips/writing/  
https://www.w3.org/WAI/WCAG22/Understanding/reading-level.html

Do NOT simplify a technical term into an inaccurate one merely to lower a readability score.

Instead:

```text
use the correct term
+
define it
```

---

# 2.41 Lists vs paragraphs

Use lists when users need to:

- compare;
- scan;
- follow steps;
- see requirements.

Example:

Instead of:

```text
Uploads must use GeoJSON, be under 100 MB and use WGS 84 coordinates.
```

use:

```text
Your file must:
• be GeoJSON
• be smaller than 100 MB
• use WGS 84 coordinates
```

when the requirements are important enough to scan independently.

---

# 2.42 Tables vs prose

Use a table when information has repeated comparable dimensions.

Example:

| Source | Resolution | Refresh |
|---|---:|---|
| Sentinel-2 | 10 m | Approx. 5 days |
| Landsat 9 | 30 m | Approx. 16 days |

Do NOT force users to extract structured comparison from prose.

---

# 2.43 Numbers

Use numerals for data values in product UI.

Prefer:

```text
4 detections
3.8 ha
12 users
```

over:

```text
four detections
three point eight hectares
```

in analytical contexts.

Typography and locale formatting MUST follow Design Token and Internationalization standards.

---

# 2.44 Thousands and decimals

Number separators MUST be locale aware.

Implementation SHOULD use locale-aware formatters rather than handcrafted string rules.

Do NOT permanently embed:

```text
1,234.56
```

as a universal format if target locales may expect another separator convention.

---

# 2.45 Hectares

Use:

```text
ha
```

for hectares in analytical UI where the audience understands the unit.

Examples:

```text
3.8 ha
1,240 ha
```

A space MUST appear between value and unit.

Do NOT use:

```text
3.8ha
```

---

# 2.46 Square kilometres

Use:

```text
km²
```

where Unicode superscript is supported.

Example:

```text
42.6 km²
```

Fallback:

```text
42.6 km2
```

SHOULD only be used where superscript cannot be represented reliably.

---

# 2.47 Percentages

Use:

```text
82%
```

or locale-appropriate equivalent.

The meaning of the denominator MUST be evident.

Do NOT present:

```text
82%
```

with no explanation when it could mean:

```text
coverage
confidence
accuracy
completion
change
```

---

# 2.48 Dates

Dates MUST be unambiguous.

Prefer:

```text
23 Sep 2026
```

or locale-aware long date.

Avoid ambiguous numeric dates such as:

```text
03/04/26
```

in international products.

Machine/API dates remain governed by the API standard.

---

# 2.49 Time zones

Time-sensitive data SHOULD show timezone where users operate across zones or audit timing matters.

Example:

```text
23 Sep 2026, 14:30 MYT
```

Relative formats MAY supplement:

```text
Updated 8 min ago
```

but SHOULD NOT replace exact timestamps where audit/reproducibility matters.

---

# 2.50 Currency

Currency MUST include an unambiguous currency identifier where multiple currencies are possible.

Prefer:

```text
MYR 12,400
USD 8,300
```

over:

```text
$8,300
```

where `$` could be ambiguous.

---

# 2.51 Coordinates

Coordinates MUST use a defined format.

Example:

```text
3.1390° N, 101.6869° E
```

or:

```text
3.1390, 101.6869
```

if the interface clearly establishes:

```text
latitude, longitude
```

Projected coordinates MUST identify their coordinate reference system where required.

Do NOT mix longitude-first and latitude-first conventions silently.

---

# 2.52 Precision

Displayed precision MUST reflect source precision.

Do not write:

```text
3.847263 ha
```

when the source only supports:

```text
3.8 ha
```

Content MUST NOT create false scientific precision.

---

# 2.53 Localisation-safe strings

Source strings MUST be written for translation.

Apple explicitly recommends simple language and writing with localisation in mind.  
https://developer.apple.com/design/human-interface-guidelines/writing

Avoid:

- idioms;
- puns;
- culturally narrow metaphors;
- gender assumptions;
- concatenated sentence fragments;
- hard-coded plural grammar.

Bad:

```ts
count + " detection" + (count === 1 ? "" : "s")
```

Prefer locale-aware message formatting.

---

# 2.54 String concatenation

Do NOT construct sentences from independently translated fragments.

Bad:

```text
"Delete " + datasetName + " permanently?"
```

because grammar/order differs between languages.

Use one translatable message:

```text
Delete {datasetName} permanently?
```

with translation tooling capable of reordering variables.

---

# 2.55 Variable context

Translation variables MUST be semantically named.

Prefer:

```text
{datasetName}
{detectionCount}
{areaHectares}
```

over:

```text
{0}
{x}
{value}
```

unless the localisation system imposes another stable convention.

---

# 2.56 Pluralisation

Plural forms MUST use localisation-aware message rules.

Do NOT assume all languages have only:

```text
singular
plural
```

The localisation system SHOULD support ICU-style plural/select semantics or an equivalent capability.

---

# 2.57 Empty-state taxonomy

Empty states MUST be classified.

Canonical types:

```text
first-use empty
valid zero data
filter/search zero result
permission empty
configuration required
processing/not ready
system failure
```

These MUST NOT all use the same generic Empty component copy.

Carbon's empty-state pattern explicitly distinguishes different reasons for absence and recommends higher specificity when intervention or troubleshooting is required.  
https://carbondesignsystem.com/patterns/empty-states-pattern/

---

# 2.58 First-use empty state

A first-use empty state SHOULD explain:

```text
what this area will contain
how content gets here
the primary first action
```

Example:

```text
No monitoring areas yet

Monitoring areas define where the system checks for
land-cover change.

[Create monitoring area]

Or explore a sample area
```

---

# 2.59 Valid zero-data state

A valid zero result may be good news.

Example:

```text
No critical detections

There are no detections above the current critical threshold
for this period.
```

Do NOT show:

```text
Nothing here
```

when zero is a meaningful analytical result.

---

# 2.60 Filtered zero state

The product MUST preserve the user's filter/search context.

Example:

```text
No detections match these filters

Region: Pahang
Confidence: ≥ 90%
Date: Last 7 days

[Clear filters]
```

Do not imply the entire dataset is empty.

---

# 2.61 Processing empty state

Where data has not yet arrived:

```text
Imagery is still processing

The 18 Sep acquisition is being processed.
Detections will appear here when processing completes.
```

If the user can safely leave, say so.

---

# 2.62 Sample content

Sample data MAY accelerate first value.

Sample content MUST be unmistakably labelled:

```text
Sample
Demo
Example data
```

It MUST NOT look like the user's real environmental data.

Sample data SHOULD demonstrate a realistic complete workflow rather than decorative fake charts.

---

# 2.63 Time to first value

Onboarding SHOULD minimise the time between:

```text
account/workspace entry
```

and:

```text
first meaningful outcome
```

The first meaningful outcome MAY be:

```text
viewing a map
loading a dataset
creating a monitoring area
reviewing a real detection
running a sample analysis
```

The system SHOULD measure this as a product funnel rather than assuming signup completion equals activation.

---

# 2.64 Progressive onboarding

Contextual help SHOULD generally be preferred to forced upfront tutorials.

NN/g reports that upfront tutorials are often skipped, interrupt users, and are easily forgotten; contextual guidance presented when users need it is more likely to match the task.  
https://www.nngroup.com/articles/onboarding-tutorials/

Apple likewise recommends onboarding that is fast and optional and suggests contextually relevant tips while users perform the associated task.  
https://developer.apple.com/design/human-interface-guidelines/onboarding

---

# 2.65 Product tours

A mandatory multi-step product tour SHOULD NOT be the default onboarding mechanism.

Use a tour only when:

- interaction is genuinely novel;
- safety/compliance requires explanation;
- the user cannot reasonably discover the next action;
- user research validates the need.

Do NOT highlight every navigation item sequentially.

---

# 2.66 Contextual tips

A contextual tip SHOULD appear only when:

```text
the user is in the relevant context
+
the information is likely to help now
```

Example:

```text
Tip:
Draw a polygon to limit analysis to a specific area.
```

shown when the user activates area creation.

Not:

```text
Tip:
You can export reports!
```

displayed during unrelated work.

---

# 2.67 Dismissal and recall

Contextual help MUST be dismissible.

Important help SHOULD be recoverable later.

NN/g specifically recommends making contextual help easy both to dismiss and to recall when needed.  
https://www.nngroup.com/articles/onboarding-tutorials/

A dismissed onboarding tip MUST NOT return every session unless new circumstances justify it.

---

# 2.68 Onboarding checklists

Checklists MAY be useful when setup contains independent meaningful tasks.

Example:

```text
Set up your workspace

✓ Create workspace
✓ Invite a reviewer
□ Create monitoring area
□ Add imagery source
□ Review first detection
```

Checklist steps SHOULD reflect user value, not administrative busywork.

Avoid:

```text
Upload profile picture
Read our blog
Watch product video
```

as required activation steps unless genuinely needed.

---

# 2.69 Checklist completion

A checklist MUST distinguish:

```text
completed
skipped
not applicable
```

where relevant.

Completion SHOULD derive from real system state rather than a user manually checking boxes.

---

# 2.70 Skip paths

Non-required onboarding MUST include a clear skip path.

Use:

```text
Skip for now
```

or:

```text
Explore on my own
```

where appropriate.

The product MUST remain usable after skip.

---

# 2.71 Re-engagement

Re-engagement MAY occur when there is evidence the user would benefit from help.

Examples:

```text
repeated failed upload
unused configured data source
incomplete required setup
new role gained
```

Re-engagement MUST NOT be driven solely by marketing desire to maximise feature exposure.

---

# 2.72 Nagging limits

The same non-critical prompt SHOULD NOT repeatedly appear after explicit dismissal.

The product SHOULD define:

```text
dismissal period
maximum repeat frequency
trigger condition
```

for re-engagement prompts.

---

# 2.73 Help hierarchy

Help SHOULD be provided at the smallest useful scope first.

Canonical hierarchy:

```text
self-explanatory UI
↓
label / help text
↓
contextual inline help
↓
tooltip
↓
linked documentation
↓
tutorial
↓
support
```

Do NOT send users to a 20-page manual when one sentence beside a field would solve the problem.

---

# 2.74 Inline help

Inline help SHOULD answer a question users are likely to have at that location.

Example:

```text
Minimum mapping unit

The smallest area the classification will report as a separate feature.

[Learn about mapping units]
```

Inline help SHOULD NOT reproduce entire documentation sections.

---

# 2.75 Documentation structure

Product documentation SHOULD be organised around user intent.

Canonical documentation categories:

```text
Get started
Concepts
How-to guides
Reference
Troubleshooting
Release notes
Glossary
```

These categories MUST remain distinguishable.

A conceptual explanation SHOULD NOT be hidden inside API reference.

---

# 2.76 Getting-started documentation

Getting-started content SHOULD take users to a meaningful result.

Example:

```text
1. Create a monitoring area
2. Add imagery
3. Run the first analysis
4. Review one detection
```

Avoid introductions that spend several pages describing company history before the first task.

---

# 2.77 Tutorials

Tutorials SHOULD be task-based and produce an outcome.

Example:

```text
Detect land-cover change in a sample area
```

is stronger than:

```text
Dashboard tutorial
```

A tutorial SHOULD state:

```text
what you will build/do
what you need
approximate scope
what you will learn
```

without forcing unnecessary prerequisites.

---

# 2.78 Reference documentation

Reference documentation SHOULD favour predictable structure over narrative.

Example:

```text
Layer opacity

Type:
Number

Range:
0–100%

Default:
100%

Affects:
Map rendering only
```

Reference pages MUST be searchable.

---

# 2.79 Glossary

The glossary SHOULD provide canonical definitions for domain terms.

Glossary definitions MUST match terms in:

- UI;
- docs;
- support;
- training.

A glossary MUST NOT be used to excuse unnecessary jargon in ordinary UI.

---

# 2.80 FAQ

FAQ MUST NOT become a dumping ground for content that lacks an information architecture.

If a question is:

```text
How do I export detections?
```

and export is a normal workflow, the answer belongs in:

```text
Export detections
```

documentation.

FAQ is appropriate for genuine recurring questions that do not fit more natural structures.

---

# 2.81 Contact support

Support entry points SHOULD state:

```text
channel
expected response target
available hours
scope
emergency path where relevant
```

Example:

```text
Enterprise support

Mon–Fri, 09:00–18:00 MYT
Target initial response: within 4 business hours

[Contact support]
```

Only publish an SLA if the organisation actually commits to it.

Do NOT label an aspirational response time as an SLA.

---

# 2.82 Support-form copy

Ask only for information required to diagnose the issue.

Where safe and permissioned, the product SHOULD automatically attach:

```text
workspace ID
browser/app version
error reference
relevant operation ID
```

rather than asking users to manually transcribe them.

Sensitive data MUST follow the Security standard.

---

# 2.83 Status pages

Operational incidents SHOULD be described factually.

Canonical status structure:

```text
Investigating
Identified
Monitoring
Resolved
```

Messages SHOULD say:

```text
what is affected
who is affected if known
workaround if available
update time
next update expectation
```

Avoid:

```text
We're experiencing some turbulence
```

in serious operational incidents.

---

# 2.84 Status-page timestamps

Incident updates MUST be timestamped.

The time zone MUST be explicit or inherent in the status platform.

Resolved updates SHOULD state whether:

```text
service recovered
backlog remains
reprocessing continues
```

when relevant.

---

# 2.85 Changelog writing

Changelog entries MUST answer:

```text
what changed
who it affects
what users need to do
```

Good:

```text
Detection filters now persist in shared links

When you share a detections page, region, confidence
and date filters are included in the URL.
No action is required.
```

Avoid:

```text
Improved filtering experience
```

---

# 2.86 Breaking changes

Breaking or workflow-changing updates MUST be explicit.

Example:

```text
GeoJSON uploads now require WGS 84 coordinates

From 15 Oct 2026, uploads using another CRS will be rejected.
Reproject existing files to EPSG:4326 before uploading.
```

Do not hide breaking changes under:

```text
Various improvements
```

---

# 2.87 Content source of truth

Every governed string SHOULD have a defined source of truth.

Possible sources:

```text
localisation platform
content repository
application string catalogue
documentation CMS
```

A string MUST NOT be independently edited in several places without governance.

---

# 2.88 UI string keys

i18n keys MUST be semantic and stable.

Prefer:

```text
detections.empty.title
detections.empty.description
detections.empty.createAreaAction
```

Avoid:

```text
string_204
labelBlueButton
noDataTextNew
```

Keys SHOULD describe meaning rather than English wording.

---

# 2.89 English text as key

Do NOT use full English UI text as the persistent key where copy changes would invalidate localisation identity.

Avoid:

```json
{
  "Delete this dataset permanently?": "..."
}
```

Prefer:

```json
{
  "dataset.delete.confirmationTitle": "..."
}
```

---

# 2.90 Source-string context

Strings SHOULD provide translators enough context to understand:

```text
where the string appears
what the action does
variables
character constraints
tone
```

A translator MUST NOT need to infer whether:

```text
Open
```

means:

```text
verb
adjective
status
```

---

# 2.91 Content review workflow

High-impact content changes SHOULD follow:

```text
author
↓
domain review
↓
content/design review
↓
accessibility/i18n review where needed
↓
approval
↓
release
```

Legal/security/compliance wording MUST include required specialist review.

Routine low-risk strings MAY use lighter governance.

---

# 2.92 Domain review

Scientific/geospatial language MUST be reviewed by an appropriate domain owner when copy:

- interprets model output;
- states scientific certainty;
- defines categories;
- describes methodology;
- makes compliance claims.

A content designer MUST NOT independently convert:

```text
high model confidence
```

into:

```text
confirmed
```

for clarity.

---

# 2.93 Copy linting

Automated linting SHOULD check for:

```text
banned phrases
title case
double spaces
ambiguous buttons
forbidden terminology
straight quotes where typographic rules require otherwise
hard-coded date formats
string concatenation
```

Linting SHOULD catch mechanical violations.

It MUST NOT be treated as a substitute for content review.

---

# 2.95 AI-generated content guardrail

AI-assisted copy MUST be reviewed against the same standard as human-written copy.

AI output MUST NOT be published without review when it contains:

- invented capabilities;
- unsupported environmental claims;
- invented metrics;
- invented customer quotes;
- fabricated dates;
- false certainty;
- inappropriate friendliness;
- repeated marketing idioms.

The Anti-AI-Slop & Craft Standard remains authoritative.

---

# 2.96 Documentation source consistency

Documentation examples MUST use actual current labels.

If a button changes from:

```text
Run analysis
```

to:

```text
Start analysis
```

documentation SHOULD be updated in the same release.

Screenshots with obsolete labels SHOULD be replaced where they materially impair guidance.

---

# 2.97 Content versioning

Critical copy SHOULD be versioned where changes affect:

- contractual meaning;
- consent;
- policy;
- methodology;
- user workflow;
- regulated communication.

Content history SHOULD be auditable in regulated environments.

---

# 2.98 Readability measurement

Teams SHOULD measure readability over time.

Possible measures:

```text
sentence length
reading-level indicators
jargon density
support search queries
user comprehension tests
```

Readability formulas MUST NOT become pass/fail truth in specialist scientific products.

A short inaccurate sentence is worse than a slightly longer accurate one.

---

# 2.99 Task-success measurement

Content quality SHOULD be measured through user behavior.

Relevant metrics MAY include:

```text
task completion
validation failure rate
error recovery rate
time to first value
onboarding completion
help usage
search refinement
support escalation
```

Metrics MUST be interpreted in context.

A reduction in help usage is not automatically positive if users simply stopped finding help.

---

# 2.100 Support-ticket deflection

Documentation and inline help MAY be evaluated for support-ticket deflection.

A useful measure is:

```text
repeated support issue volume
before vs after a targeted content improvement
```

Teams SHOULD distinguish:

```text
ticket avoided because the problem became understandable
```

from:

```text
ticket not filed because support became difficult to access
```

The second is not success.

---

# 2.101 Help-search measurement

Documentation teams SHOULD monitor:

```text
zero-result searches
common queries
repeated synonyms
search exits
support escalations after search
```

These can reveal terminology or IA defects.

Search analytics MUST follow privacy requirements.

---

# 2.102 Content experiment integrity

A/B tests MAY optimise:

- comprehension;
- completion;
- discoverability;
- conversion.

They MUST NOT optimise deceptive outcomes.

Do NOT test manipulative copy designed to produce accidental:

```text
upgrades
consent
deletion
subscription retention
```

at the expense of informed choice.

---

# 2.103 Security alignment

Content MUST NOT reveal restricted information through:

- errors;
- permission messages;
- search suggestions;
- resource names;
- system identifiers.

Example:

```text
You do not have access to this resource
```

MAY be safer than naming a protected project, depending on policy.

Security determines disclosure boundaries.

---

# 2.104 Data & Database alignment

Content describing data MUST use authoritative definitions.

UI copy MUST NOT invent:

```text
risk
accuracy
confidence
freshness
status
```

independently from governed data semantics.

"0" MUST NOT be presented as "No data."

---

# 2.105 API alignment

API errors SHOULD map to user-facing states deliberately.

Do NOT surface raw API messages such as:

```text
HTTP 422: Unprocessable Entity
```

as the primary UI error.

The UI MAY retain technical references for support.

---

# 2.106 State Management alignment

Copy MUST reflect actual state.

Do NOT display:

```text
Saved
```

before persistence succeeds.

Do NOT display:

```text
Deleted
```

while deletion is still queued unless the product semantics guarantee the outcome.

Optimistic UI copy MUST match the rollback strategy.

---

# 2.107 Forms & Validation alignment

Validation copy MUST align with the canonical form rules.

GOV.UK recommends preserving entered values after validation failure and exposing both field-level errors and a summary where appropriate.  
https://design-system.service.gov.uk/patterns/validation/

The UI MUST NOT:

- erase valid input;
- display contradictory client/server messages;
- validate purely stylistic preferences as errors.

---

# 2.108 Accessibility alignment

W3C recommends:

- meaningful headings;
- meaningful link text;
- concise language;
- clear instructions;
- expanded unfamiliar acronyms;
- glossary support.

https://www.w3.org/WAI/tips/writing/

Accessibility content MUST be reviewed as part of the content system, not only implementation.

---

# 2.109 Component alignment

Content contracts SHOULD be defined per shadcn-based component.

Examples:

```text
Button:
short action label

Alert:
title + concise supporting description

Alert Dialog:
specific consequence + explicit actions

Tooltip:
supplementary information only

Empty:
title + reason + next action

Form field:
label + optional help + error
```

Components MUST NOT encourage copy structures that violate content standards.

# 4. Anti-patterns

## 4.1 Marketing language in operational UI

Do NOT write:

```text
Unlock powerful geospatial insights
```

where the actual task is:

```text
View detections
```

---

## 4.2 False scientific certainty

Do NOT upgrade:

```text
detection
```

into:

```text
confirmed event
```

without evidence.

---

## 4.3 Fake warmth

Do NOT add:

```text
Oops!
Uh-oh!
Yay!
🎉
🌱
```

automatically.

Tone follows context.

---

## 4.4 Generic error copy

Do NOT use:

```text
An error occurred
```

when a specific actionable explanation is known.

---

## 4.5 Developer errors in UI

Do NOT expose:

```text
ECONNRESET
422
TypeError
SQLSTATE
```

as end-user guidance.

---

## 4.6 Blaming language

Avoid:

```text
You entered…
You failed to…
Your input is invalid…
```

when neutral correction works.

---

## 4.7 Placeholder-only labels

Placeholder text MUST NOT act as the only field label.

---

## 4.8 Help-text repetition

Do NOT write:

```text
Email address
Enter your email address
```

without additional useful guidance.

---

## 4.9 Vague actions

Avoid:

```text
OK
Go
Proceed
Yes
No
Submit
```

when a more descriptive action is possible.

---

## 4.10 Hidden consequences

Do NOT hide destructive, billing, or permission consequences behind tooltips.

---

## 4.11 Zero-data ambiguity

Do NOT use:

```text
No data
```

for all empty conditions.

---

## 4.12 Tutorial-first onboarding

Do NOT force a six-step product tour before the user can act.

NN/g finds such push tutorials are often skipped and poorly retained.  
https://www.nngroup.com/articles/onboarding-tutorials/

---

## 4.13 Tip spam

Do NOT show contextual tips simply because a feature exists.

---

## 4.14 Recurring dismissed onboarding

Do NOT repeatedly reopen a dismissed onboarding prompt without a new contextual reason.

---

## 4.15 FAQ landfill

Do NOT place every undocumented workflow into FAQ.

---

## 4.16 Changelog vagueness

Avoid:

```text
Bug fixes and improvements
```

when the user-impacting changes can be named.

---

## 4.17 Fake SLA

Do NOT publish:

```text
Response within 1 hour
```

if support operations do not actually guarantee it.

---

## 4.18 String concatenation

Do NOT construct translatable user-facing sentences from fragments.

---

## 4.19 English-specific grammar assumptions

Do NOT assume:

```text
word order
plural count
gender
date order
```

will remain valid after translation.

---

## 4.20 Arbitrary readability target

Do NOT rewrite domain content into inaccurate language merely to improve a readability score.

---

## 4.21 Copy as layout filler

Text MUST NOT be added merely because a card appears empty.

---

## 4.22 Tooltip documentation

A tooltip is not a documentation system.

---

## 4.23 Success-toast dependence

Do NOT make an important persistent state change understandable only through a toast that disappears.

---

## 4.24 Marketing paywalls

Do NOT obscure plan limitations behind motivational language.

---

## 4.25 AI-slop copy

The product MUST reject interchangeable generic phrases such as:

```text
Elevate your workflow
Unlock smarter insights
Empower your team
Transform your data journey
```

They contain little product-specific meaning.

# 5. Copy Acceptance Checklist

## Voice

- [ ] Copy is precise.
- [ ] Copy is calm.
- [ ] Copy is evidence-led.
- [ ] Copy avoids unsupported environmental conclusions.
- [ ] Voice matches the domain.
- [ ] Tone matches the situation.
- [ ] Routine actions are not over-celebrated.
- [ ] Serious states are not made playful.

## Terminology

- [ ] Canonical product terminology is used.
- [ ] UI and documentation terminology match.
- [ ] Technical terms are defined where necessary.
- [ ] Acronyms are expanded on first meaningful use where appropriate.
- [ ] Detection/verification/legal conclusions are distinguished.
- [ ] Confidence is not mislabeled accuracy.
- [ ] Missing data is not called zero.

## Headings

- [ ] Page heading identifies page/task.
- [ ] Section headings communicate content.
- [ ] Generic headings such as "Details" are avoided where a specific term exists.
- [ ] Heading hierarchy is logical.
- [ ] Sentence case is used unless exception is documented.

## Buttons

- [ ] Action is clear without surrounding paragraph where practical.
- [ ] Verb + object is used where helpful.
- [ ] Destructive action names the object.
- [ ] `Yes` / `No` is avoided.
- [ ] `Submit` is used only where no clearer action exists.
- [ ] Primary label matches actual immediate result.

## Forms

- [ ] Field has a persistent label.
- [ ] Help text adds new information.
- [ ] Input example is realistic.
- [ ] Validation identifies correction.
- [ ] User is not blamed.
- [ ] Error state preserves entered data.
- [ ] Client/server messages are consistent.

## Errors

- [ ] Error identifies what failed.
- [ ] Recovery path is given if available.
- [ ] System errors are distinct from input errors.
- [ ] Technical reference is secondary.
- [ ] Error does not leak restricted data.
- [ ] Error does not over-apologise.
- [ ] Error state is not represented only by colour.

## Success

- [ ] Message confirms what completed.
- [ ] Important state persists after transient notification disappears.
- [ ] Success is not over-celebrated.
- [ ] Saved/published/deleted state reflects authoritative system state.

## Empty states

- [ ] Empty-state type is identified.
- [ ] Reason for emptiness is clear.
- [ ] Next action is clear.
- [ ] Sample content is labelled.
- [ ] Valid zero is distinguished from failure.
- [ ] Filtered zero preserves active filters.
- [ ] Processing state is distinguished from no data.

## Onboarding

- [ ] Time-to-first-value is defined.
- [ ] Onboarding is optional where possible.
- [ ] Contextual guidance is preferred over upfront tours.
- [ ] Tips appear in relevant context.
- [ ] Tips can be dismissed.
- [ ] Important help can be recalled.
- [ ] Sample data is distinguishable from real data.
- [ ] Checklist steps map to meaningful product value.
- [ ] Re-engagement frequency is controlled.

## Help

- [ ] Inline help is used before external docs where sufficient.
- [ ] Documentation is task organised.
- [ ] Concepts, how-to and reference are separated.
- [ ] FAQ is not a dumping ground.
- [ ] Glossary uses canonical definitions.
- [ ] Support channels state realistic availability.
- [ ] SLA claims are contractual/operationally valid.
- [ ] Status pages provide factual incident updates.
- [ ] Changelog describes actual user impact.

## Numbers and units

- [ ] Number formatting is locale aware.
- [ ] Value and unit are separated correctly.
- [ ] `%` meaning is clear.
- [ ] `ha` and `km²` are used consistently.
- [ ] Date is unambiguous.
- [ ] Time zone is supplied where required.
- [ ] Currency is unambiguous.
- [ ] Coordinate order is explicit.
- [ ] Precision matches source accuracy.

## Localisation

- [ ] String is complete and translatable.
- [ ] No concatenated sentence fragments.
- [ ] No untranslatable pun/idiom.
- [ ] Pluralisation uses localisation rules.
- [ ] Variables have semantic names.
- [ ] Translator context exists where necessary.
- [ ] UI allows text expansion.
- [ ] No content assumes English word order.

## Content operations

- [ ] String source of truth is known.
- [ ] i18n key is semantic.
- [ ] Content owner exists.
- [ ] Domain review completed where needed.
- [ ] Legal/security review completed where needed.
- [ ] Banned-phrase lint passes.
- [ ] Documentation labels match product.
- [ ] Content changes are versioned where required.

## Measurement

- [ ] Task success is measured.
- [ ] Repeated validation errors are monitored.
- [ ] Zero-result help search is monitored.
- [ ] Time to first value is measured where onboarding matters.
- [ ] Support-ticket themes are reviewed.
- [ ] Readability metrics are advisory, not sole pass/fail.
- [ ] Content experiments do not use dark patterns.

# 6. Canonical Copy Patterns

## Error

# 7. Canonical Summary

The Content, Microcopy, Help & Onboarding standard follows this hierarchy:

```text
user need
↓
truth / domain semantics
↓
content hierarchy
↓
voice + contextual tone
↓
microcopy
↓
component state
↓
accessibility + localisation
↓
help / documentation
↓
measurement + governance
```

The governing rules are:

```text
Voice stays stable.
Tone changes with context.

Write like a competent domain specialist,
not a marketer.

Be precise about what the system knows.

Detection is not verification.
Confidence is not automatically accuracy.
Overlap is not automatically violation.
Missing data is not zero.

Front-load meaning.

Use short headings,
short paragraphs,
lists and tables.

Buttons describe actions.

Errors describe the problem
and how to recover.

Do not blame users.

Do not use Yes/No
when the action can be named.

Empty states explain:
why it is empty,
what happens next,
and what the user can do.

Onboarding should accelerate first value.

Prefer contextual help
to mandatory tours.

Help should exist at the smallest useful scope.

Documentation is organised by user intent,
not by organisational ownership.

FAQ is not a content landfill.

Numbers, units, dates, currencies
and coordinates are part of the content contract.

Source strings must be localisation-safe.

Do not concatenate translated sentences.

Strings need owners,
keys,
review,
versioning
and measurable outcomes.

Reject generic AI-slop copy.

Clarity outranks personality.
Accuracy outranks brevity.
User understanding outranks marketing tone.
```

A **Gold Standard 2026** interface MUST allow users to understand:

```text
What is this?

What happened?

What does this value mean?

How certain is it?

What do I need to do?

What will this button do?

What happens if I delete this?

Why is this page empty?

Can I recover?

Where can I get help?

Is this sample data or my data?

Is this observation, inference, or verification?

When was this information last updated?
```

If the interface requires users to infer those answers from colour, icons, implementation details, or product lore, the content contract is incomplete.
