This version treats AI output as a stateful, probabilistic product surface rather than ordinary static content. It separates **generation state, task/tool progress, uncertainty, provenance, memory, and cost** so the interface never implies guarantees the underlying model or system cannot make.

# AI UX Guidelines — Gold Standard 2026

**Canonical placement:** AI/LLM → AI UX → Content & UX Writing → Accessibility  
**Status:** Gold Standard 2026  
**Component baseline:** shadcn/ui  
**Accessibility baseline:** WCAG 2.2 AA minimum  
**Core principle:** generated output MUST remain identifiable, interruptible, inspectable, and understandable as probabilistic AI output

---

# 1. Purpose

## 1.1 Scope

This standard defines the canonical UX requirements for interfaces powered by generative AI, language models, multimodal models, agents, retrieval systems, and AI-assisted workflows.

It covers:

- AI disclosure;
- streaming output;
- partial generation;
- progress and processing states;
- reasoning/progress disclosure;
- citations and sources;
- uncertainty communication;
- edit, retry, regenerate, and stop controls;
- conversation and prompt state;
- memory and personalization;
- generated-content accessibility;
- errors and refusals;
- rate limits;
- cost, usage, token, credit, or quota visibility;
- external tools and actions;
- loading and latency;
- recoverability;
- model and capability changes;
- high-impact and consequential workflows.

This standard applies to:

- conversational assistants;
- copilots;
- AI search;
- generative editors;
- AI form assistance;
- document generation;
- coding assistants;
- AI agents;
- multimodal interfaces;
- AI-supported analytics;
- embedded generative components.

---

## 1.2 Design objective

AI interfaces MUST help users distinguish:

1. **what they provided;**
2. **what the AI generated;**
3. **what external sources supplied;**
4. **what the system actually did;**
5. **what remains uncertain;**
6. **what is remembered or retained;**
7. **what will cost money, credits, or quota.**

The interface MUST NOT present probabilistic output as deterministic system truth.

The user MUST remain in control of:

- submission;
- interruption;
- correction;
- regeneration;
- consequential actions;
- stored personalization where applicable.

AI UX MUST optimize for:

- clear provenance;
- recoverability;
- appropriate trust;
- understandable uncertainty;
- user agency;
- accessibility;
- security;
- task completion.

The interface MUST NOT optimize solely for perceived intelligence, anthropomorphism, engagement, or uninterrupted generation.

---

## 1.3 AI output is not ordinary application output

Generated content MAY be:

- incorrect;
- incomplete;
- stale;
- inconsistent;
- unsupported by cited evidence;
- sensitive to prompt wording;
- different across retries.

The surrounding interface MUST therefore preserve distinctions that conventional deterministic UI may not require.

For example:

- a generated answer is not equivalent to a validated database record;
- a model statement that an action succeeded is not equivalent to an API success response;
- a plausible citation is not equivalent to a verified source;
- a progress message generated by a model is not equivalent to measured execution progress.

Canonical application state MUST remain authoritative.

---

## 1.4 Relationship to other standards

AI UX implementations MUST conform to corpus standards for:

- **Security** — prompt injection, tool authorization, secrets, untrusted content, data disclosure;
- **Data & Database** — storage, retention, provenance, deletion, user data, generated records;
- **API** — streaming protocols, cancellation, errors, retries, tool calls, rate limiting;
- **State Management** — conversation state, branches, partial output, pending actions, memory state;
- **Forms & Validation** — prompts, structured inputs, generated form values, validation;
- **Accessibility** — live regions, keyboard control, semantic output, generated-content structure;
- **Design Tokens** — status, provenance, AI labels, warning, loading, citation and confidence treatment;
- **Components** — shadcn/ui primitives;
- **Patterns** — errors, loading, confirmations, overlays, search, editing, undo;
- **Content & UX Writing** — disclosure, uncertainty, refusals, action labels and explanatory language.

An AI SDK, model provider, agent framework, or chat library MUST NOT create a parallel UX, accessibility, security, or state-management architecture.

# 2. Rules

## 2.1 AI involvement MUST be disclosed

Users MUST be able to determine when content or interaction is materially generated or mediated by AI.

Disclosure MUST be clear enough to distinguish AI-generated output from:

- user-authored content;
- human-authored content;
- authoritative system data;
- quoted source material.

Appropriate disclosure MAY include:

- `AI-generated`;
- `Generated with AI`;
- an established AI identity;
- persistent assistant identity within an explicitly AI product.

A disclosure MUST NOT depend only on:

- a decorative sparkle icon;
- colour;
- an unfamiliar logo;
- fine print shown only once.

Where the entire product is unambiguously an AI assistant, every message need not repeat an intrusive AI warning.

Where AI output is inserted into an otherwise conventional workflow, the origin SHOULD remain more explicit.

---

## 2.2 AI identity MUST NOT imply human identity

The UI MUST NOT falsely imply that an AI system:

- is a human employee;
- personally reviewed information when it did not;
- possesses emotions or intentions as factual system state;
- independently performed an external action when no such action occurred.

Conversational language MAY be used.

Conversational tone MUST NOT obscure the distinction between generated language and verified application state.

---

## 2.3 Generated content MUST remain identifiable after insertion

When generated content is inserted into another artifact, the product SHOULD preserve appropriate provenance where that provenance remains relevant.

Examples include:

- AI-generated draft status;
- generation history;
- document activity history;
- metadata indicating AI assistance.

Provenance MUST NOT be displayed so aggressively that ordinary editing becomes impractical.

Products SHOULD define when AI provenance:

- remains visible;
- moves into history/metadata;
- is intentionally removed.

---

## 2.4 Streaming SHOULD improve latency perception, not correctness perception

Text MAY stream incrementally when generation latency makes progressive display useful.

Streaming MUST NOT imply that early tokens are:

- more certain;
- validated;
- final.

Partial output MUST be visually understood as incomplete while generation continues.

The UI SHOULD provide a clear generation state such as:

- `Generating`;
- `Working`;
- `Responding`.

A blinking cursor MAY supplement generation state but MUST NOT be the only indication.

---

## 2.5 Streaming MUST preserve readability

Streaming cadence SHOULD prioritize readable output over displaying every network chunk immediately.

The client MAY buffer small token or text chunks to reduce visual jitter.

Streaming MUST NOT cause:

- excessive layout jumping;
- constantly shifting controls;
- repeated scroll instability;
- unusable partial Markdown;
- visible raw protocol fragments.

Structured elements SHOULD render coherently.

For example, the client SHOULD avoid exposing unstable partially parsed:

- tables;
- code fences;
- mathematical expressions;
- links.

---

## 2.6 Partial output MUST have explicit lifecycle semantics

The state model MUST distinguish:

- pending;
- streaming;
- complete;
- stopped;
- failed;
- refused;
- cancelled.

A stopped response MUST NOT appear identical to a completed response.

A failed stream MUST preserve valid partial content where doing so is useful and safe.

Partial output SHOULD be labelled when ambiguity is possible.

A network interruption MUST NOT silently convert partial content into a completed answer.

---

## 2.7 Partial output persistence

Products MUST define whether partially generated responses are retained.

If a response is stopped manually, the product SHOULD preserve already generated useful content unless:

- the content is invalid;
- security requirements prohibit it;
- the workflow explicitly treats generation as atomic.

A retry MUST NOT unexpectedly erase useful previous output.

Conversation history SHOULD preserve enough state to distinguish:

- stopped response;
- completed response;
- failed generation.

---

## 2.8 Stop control

A visible `Stop` control SHOULD be available during materially long generation.

Stopping MUST interrupt presentation promptly.

Where infrastructure permits, stopping SHOULD also cancel unnecessary backend generation or tool execution.

The UI MUST NOT falsely claim backend cancellation if only client rendering stopped.

Stopping text generation MUST NOT automatically cancel a consequential external action that has already been committed.

External action cancellation MUST follow that action's own API semantics.

---

## 2.9 Stop control accessibility

The stop control MUST be:

- keyboard operable;
- accessible by name;
- reachable without chasing a moving interface.

Its position SHOULD remain stable while content streams.

The user MUST NOT have to scroll to the bottom of a rapidly growing answer merely to stop generation.

---

## 2.10 Generation controls MUST reflect current state

Controls such as:

- Send;
- Stop;
- Regenerate;
- Retry;
- Continue

MUST only appear or enable when their semantics are valid.

A `Regenerate` action MUST NOT be presented while the original request is still executing unless parallel generation is intentionally supported.

`Retry` SHOULD represent retrying a failed operation.

`Regenerate` SHOULD represent requesting a new generated result.

These concepts SHOULD NOT be conflated.

---

## 2.11 Regeneration MUST preserve history

Regenerating SHOULD NOT silently overwrite the only copy of a previous response.

Products SHOULD preserve:

- alternative generation history;
- a branch;
- version navigation;
- another recoverable representation.

The user SHOULD be able to understand that different generations answer the same preceding context.

Regeneration MUST NOT silently duplicate consequential tool actions that occurred during the previous response.

---

## 2.12 Edit-and-resubmit semantics

Users SHOULD be able to correct prompts or instructions without rebuilding an entire workflow.

Editing an earlier message MUST define what happens to subsequent state.

The product SHOULD either:

- create a branch;
- clearly replace dependent subsequent content;
- explicitly warn that later responses will be recomputed.

Editing historical input MUST NOT silently leave dependent AI output presented as if it still followed from the new input.

---

## 2.13 Conversation branching

Products supporting alternative generations or edited historical prompts SHOULD model branches explicitly.

Branches MUST NOT share mutable state in a way that creates invisible cross-branch contamination.

External actions already performed in one branch MUST NOT appear undone merely because the user navigates to another conversational branch.

Branch switching SHOULD preserve:

- prompt lineage;
- relevant attachments;
- source context;
- tool results associated with that branch.

---

## 2.14 Thinking and processing disclosure

The interface MAY indicate that the system is processing.

Appropriate labels include:

- `Working`;
- `Analyzing`;
- `Searching sources`;
- `Running code`;
- `Preparing result`.

Processing disclosure SHOULD describe **observable task state**, not simulate private mental activity.

The UI MUST NOT fabricate detailed internal reasoning steps merely to make the system appear intelligent.

---

## 2.15 Hidden chain-of-thought MUST NOT be a normal UX surface

Raw private model chain-of-thought MUST NOT be presented as routine user-visible content.

Where useful, the product MAY expose:

- a concise reasoning summary;
- an answer explanation;
- assumptions;
- methodology;
- sources;
- verifiable intermediate results.

These MUST be generated as user-facing explanatory content, not represented as a verbatim dump of private model reasoning.

OpenAI's published reasoning guidance similarly distinguishes hidden reasoning tokens from user-visible reasoning summaries. citeturn919553search0turn919553search3

---

## 2.16 Progress MUST represent real progress

Progress UI MUST distinguish:

- unknown-duration processing;
- measurable deterministic progress;
- model-generated narration.

A percentage MUST NOT be shown unless the system has a defensible measurement for that percentage.

A model saying:

`About 80% complete`

MUST NOT be treated as measured system progress merely because the statement is plausible.

Use indeterminate progress when true completion cannot be quantified.

---

## 2.17 Tool progress SHOULD expose meaningful phases

Agentic or tool-using systems SHOULD expose meaningful execution phases when doing so helps users understand latency or control actions.

Examples include:

- `Searching`;
- `Reading 4 sources`;
- `Running analysis`;
- `Creating draft`;
- `Uploading file`.

Task status MUST derive from actual orchestration state where available.

Generated status prose MUST NOT substitute for real execution telemetry.

---

## 2.18 Progress detail MUST remain proportionate

Routine generation SHOULD NOT expose a verbose activity log.

Detailed execution traces MAY be appropriate for:

- developer tools;
- long-running agents;
- auditable workflows;
- debugging.

Consumer-facing workflows SHOULD expose only information that materially supports:

- trust;
- interruption;
- comprehension;
- diagnosis.

---

## 2.19 Citations MUST be attached to supported claims

When a response cites external evidence, the citation SHOULD appear close to the claim or passage it supports.

A generic source list at the end MUST NOT imply that every source supports the entire answer.

Citation UI SHOULD allow users to determine:

- source title;
- publisher or origin;
- relevant location where available;
- link or document identity.

The interface MUST NOT generate visual citation markers that have no associated source object.

---

## 2.20 Citation presence MUST NOT imply universal correctness

Citations demonstrate provenance, not automatic truth.

The UI MUST NOT use language or styling that implies:

- “cited” means “verified”;
- one citation validates unrelated claims;
- retrieval eliminates model error.

A citation SHOULD support the specific nearby claim.

Where source evidence is conflicting or incomplete, the generated content SHOULD communicate that condition.

---

## 2.21 Source identity MUST be clear

Sources MUST be distinguishable from generated content.

Source display SHOULD identify:

- source name;
- document/page title;
- relevant publication or update date where material;
- source type where useful.

Raw URLs SHOULD NOT be the only human-readable source label where a meaningful title is available.

---

## 2.22 Source availability MUST be represented accurately

If a citation references content the user cannot access, the interface SHOULD communicate the limitation.

Examples include:

- permission required;
- internal source;
- paywalled;
- expired link;
- removed source.

A source MUST NOT appear accessible if selecting it will inevitably fail for the current user.

---

## 2.23 Quotation and paraphrase MUST remain distinguishable

Direct quotation MUST use appropriate quotation treatment.

Generated paraphrase MUST NOT be presented with quotation styling suggesting verbatim source text.

The product SHOULD preserve source links at an appropriate granularity for quoted material.

---

## 2.24 Citation inspection MUST be accessible

Citation markers MUST be keyboard operable where interactive.

They MUST have meaningful accessible names.

A screen reader SHOULD be able to determine which source a citation references without hearing meaningless text such as:

`link 3`.

Citation popovers or previews MUST follow the Overlay and Accessibility standards.

---

## 2.25 Uncertainty MUST be communicated when material

Generated content SHOULD disclose uncertainty when uncertainty could materially affect a user's decision or interpretation.

Uncertainty SHOULD be communicated near the affected claim.

Acceptable forms include:

- `The available data does not establish…`;
- `I could not verify…`;
- `This is an estimate…`;
- `Sources disagree…`;
- `The result depends on…`.

Generic disclaimers SHOULD NOT be repeated mechanically on every answer.

---

## 2.26 Different kinds of uncertainty MUST remain distinct

Products SHOULD distinguish where relevant between:

- missing information;
- conflicting evidence;
- probabilistic prediction;
- model uncertainty;
- estimation;
- ambiguous user intent;
- unavailable live data;
- unverified generated inference.

The interface MUST NOT collapse all of these into a vague:

`AI may make mistakes`

message when more specific information is available.

---

## 2.27 Unsupported numeric confidence MUST NOT be shown

The product MUST NOT display precise confidence percentages unless the value has a defined, validated interpretation for the task.

A model-generated `93% confident` statement MUST NOT be presented as calibrated statistical confidence by default.

Numeric probability MAY be shown when it comes from an appropriate validated model, forecast, or statistical computation and its meaning is clear.

---

## 2.28 Confidence MUST NOT become decorative scoring

Responses MUST NOT receive arbitrary:

- confidence bars;
- green/yellow/red truth indicators;
- trust scores

without validated semantics.

Visual certainty cues MUST NOT imply guarantees stronger than the underlying evidence supports.

---

## 2.29 Corrections SHOULD be direct

When the system identifies an earlier error, it SHOULD clearly correct it.

The UI SHOULD preserve enough context to determine:

- what changed;
- which answer is current.

A correction MUST NOT silently mutate historical content where auditability matters.

For lightweight conversational products, replacing content MAY be acceptable only if the product clearly indicates that an edit occurred.

---

## 2.30 Memory concepts MUST be separated

AI products MUST distinguish between:

- current conversation context;
- persistent user memory;
- account preferences;
- connected-source data;
- temporary tool state;
- application history.

These concepts MUST NOT all be labelled generically as `memory`.

Users SHOULD be able to understand what type of information may affect future responses.

---

## 2.31 Persistent memory MUST be inspectable

If the system maintains persistent personalized memory, the product SHOULD provide a user-accessible way to understand:

- that persistent memory exists;
- what categories of information may be retained;
- how it affects responses;
- how to disable, update, or remove it where supported.

Memory controls MUST NOT be hidden behind misleading terminology.

---

## 2.32 Memory changes MUST NOT be deceptive

When the interface states that something has been:

- remembered;
- forgotten;
- deleted;
- disabled

that statement MUST reflect actual system state.

The model MUST NOT claim successful memory mutation merely because it generated the words:

`I'll remember that`.

The application MUST verify the underlying persistence result before communicating success.

---

## 2.33 Sensitive memory requires stricter treatment

Products SHOULD minimize persistent storage of sensitive information.

Where sensitive memory is allowed, Security and privacy requirements MUST govern:

- consent;
- purpose;
- retention;
- encryption;
- access;
- deletion;
- auditability.

Generated personalization MUST NOT reveal sensitive stored context unexpectedly in a shared or inappropriate surface.

---

## 2.34 Memory source SHOULD remain understandable

Where practical, users SHOULD be able to determine why a piece of personalized context is being used.

The product MAY identify context as coming from:

- current conversation;
- a user preference;
- persistent memory;
- a connected source.

The UI SHOULD NOT expose unnecessary internal retrieval details.

---

## 2.35 Connected sources MUST remain distinct from memory

Access to a connected:

- email account;
- document store;
- calendar;
- database;
- CRM

MUST NOT be described as the model “remembering” that content.

Connected data is external source access and MUST follow:

- authentication;
- authorization;
- source attribution;
- connector permission rules.

---

## 2.36 External actions MUST be distinguished from generated suggestions

The UI MUST clearly distinguish between:

- suggesting an action;
- drafting an action;
- requesting approval;
- executing an action;
- confirming completion.

A generated sentence such as:

`I've sent the email`

MUST NOT be displayed as completion unless the mail operation actually succeeded.

Authoritative tool or API state MUST determine action completion.

---

## 2.37 Consequential actions require explicit semantics

Actions with meaningful external effects SHOULD require appropriate confirmation according to the Security and Pattern standards.

Examples include:

- sending messages;
- purchasing;
- deleting records;
- publishing content;
- changing permissions;
- scheduling;
- transferring funds.

Confirmation MUST identify:

- the action;
- target;
- material parameters.

Users MUST NOT be asked to approve an opaque bundle of hidden actions.

---

## 2.38 Tool failures MUST remain distinct from model failures

A system SHOULD distinguish:

- model generation failure;
- tool failure;
- network failure;
- authorization failure;
- validation failure;
- source retrieval failure.

The generated assistant MUST NOT invent a successful tool result when the actual tool failed.

---

## 2.39 Errors MUST preserve user work

Technical failures SHOULD preserve:

- prompt text;
- attachments where safe;
- partial generated output;
- form values;
- relevant tool state.

A retry SHOULD be possible without reconstructing the entire request where practical.

Errors MUST NOT clear the conversation merely because the latest generation failed.

---

## 2.40 Error messages MUST identify next action

An error message SHOULD answer:

1. what failed;
2. whether user work was preserved;
3. what the user can do next.

Prefer:

`The response stopped because the connection was interrupted. Your prompt is saved. Retry generation.`

over:

`Something went wrong.`

Technical details MAY be available through expandable diagnostic UI when appropriate.

---

## 2.41 Refusals MUST be distinguishable from errors

A policy or safety refusal MUST NOT look like:

- a network failure;
- a server error;
- a rate limit;
- a broken model.

A refusal SHOULD state the relevant limitation concisely.

Where appropriate, it SHOULD provide a safer or supported alternative.

The UX MUST NOT encourage repeated retry loops for requests that will predictably remain unsupported.

---

## 2.42 Refusals MUST preserve dignity and clarity

Refusal language SHOULD be:

- neutral;
- concise;
- specific enough to be useful;
- non-accusatory.

The system SHOULD focus on what it can support rather than moralizing about the request.

Internal policy text, hidden safety classification, or security-sensitive decision logic SHOULD NOT be exposed merely to justify a refusal.

---

## 2.43 Capability limits MUST be stated accurately

The AI MUST NOT imply capabilities it does not have.

The product SHOULD clearly communicate when it cannot:

- access current external data;
- open a source;
- execute a tool;
- observe the physical world;
- retain information;
- perform work asynchronously.

Capability limitations SHOULD appear when relevant, not as permanent clutter.

---

## 2.44 Retry MUST avoid uncontrolled duplication

Retrying MUST NOT duplicate external side effects accidentally.

If a request failed after an external action may have succeeded, the system MUST determine or communicate the ambiguous execution state before repeating the action where practical.

Idempotency SHOULD be used for consequential operations where supported by the API standard.

---

## 2.45 Cost and quota MUST be visible before material commitment

When an AI action has meaningful user-visible cost, credits, quota, or billing consequences, the product SHOULD communicate that consequence before execution.

The UI SHOULD show the most understandable available unit.

Examples include:

- credits;
- included generations;
- estimated cost;
- remaining quota.

Users MUST NOT need to understand tokens merely to control ordinary product spending unless tokens are themselves the product's contractual billing unit.

---

## 2.46 Estimated cost MUST be labelled as estimated

When exact cost is unknown before generation, the UI MUST distinguish:

- estimate;
- maximum;
- actual amount.

An estimate MUST NOT be presented as an exact charge.

Where practical, actual usage SHOULD be available after completion.

---

## 2.47 Cost disclosure SHOULD be proportional

Routine low-cost actions covered by a simple subscription SHOULD NOT require a confirmation dialog for every generation.

Additional cost disclosure becomes more important when:

- the action is unusually expensive;
- premium credits are consumed;
- user-configurable spending applies;
- a long-running agent can consume substantial resources.

---

## 2.48 Spending limits SHOULD be actionable

Where the product supports spend or credit limits, users SHOULD be able to understand:

- remaining allocation;
- reset date where applicable;
- what happens at exhaustion;
- how to change a limit.

A low-credit warning SHOULD appear early enough to allow informed choice.

A depleted quota MUST NOT masquerade as an AI refusal.

---

## 2.49 Model selection MUST communicate meaningful differences

If users can select models, the product SHOULD expose differences that materially affect the task, such as:

- capability;
- speed;
- cost;
- supported modalities;
- context or tool availability.

Model selection MUST NOT rely exclusively on opaque internal names when those names provide insufficient user meaning.

The UI SHOULD NOT imply that a more expensive model is automatically correct.

---

## 2.50 Automatic model changes SHOULD preserve expectations

If the system automatically routes or changes models, user-facing behaviour SHOULD remain within the promised capability contract.

Material changes affecting:

- cost;
- privacy;
- data residency;
- available tools;
- output capability

MUST follow the applicable disclosure and consent requirements.

---

## 2.51 Generated structured data MUST be validated

AI-generated values inserted into structured application state MUST pass the same validation as user-entered values.

Generated:

- dates;
- amounts;
- IDs;
- addresses;
- enum values;
- database fields

MUST NOT bypass Forms & Validation merely because they came from a model.

The model MUST NOT be treated as a schema validator.

---

## 2.52 Generated actions MUST obey authorization

A model's recommendation to call a tool MUST NOT grant permission to call that tool.

Authorization MUST be enforced by application and backend systems.

Prompt instructions MUST NOT bypass:

- tenant isolation;
- row-level permissions;
- role restrictions;
- action confirmation.

Security state remains authoritative over generated intent.

---

## 2.53 Retrieved content MUST be treated as untrusted

Content retrieved from:

- websites;
- uploaded files;
- email;
- databases;
- connected tools

MAY contain instructions intended to manipulate an AI system.

Retrieved content MUST be treated as data unless explicitly trusted as instructions by the application architecture.

The UI MUST NOT imply that all source content is safe merely because it was retrieved successfully.

---

## 2.54 Prompt injection MUST NOT become a user burden by default

Security controls SHOULD handle ordinary prompt-injection resistance within the system architecture.

Users SHOULD NOT be expected to manually inspect hidden prompts or retrieved instructions to keep the application safe.

When suspicious content materially affects the task, the interface MAY explain that some source instructions were ignored or could not safely be followed.

---

## 2.55 Generated links MUST be safe

Generated links MUST be rendered through the canonical link component and security controls.

The displayed destination SHOULD be understandable when clicking could have meaningful consequences.

The product SHOULD defend against:

- dangerous schemes;
- deceptive destination labels;
- untrusted auto-navigation.

Generated content MUST NOT automatically navigate to arbitrary destinations without user intent.

---

## 2.56 Streaming accessibility requires a separate announcement strategy

Visual token streaming MUST NOT automatically cause every text mutation to be announced by assistive technology.

Doing so can make the interface unusably verbose.

The product SHOULD expose semantic generation status separately from raw visual token updates.

WCAG 2.2 requires status messages to be programmatically determinable without taking focus, while W3C guidance also warns against making interfaces excessively chatty for assistive-technology users. citeturn919553search1turn919553search5

---

## 2.57 Live status SHOULD use appropriate semantics

Generation and tool status SHOULD use an appropriate accessible status mechanism.

`role="status"` or an equivalent polite status mechanism MAY be used for ordinary asynchronous status changes. W3C documents `role="status"` as a technique for notifying assistive technology without moving focus. citeturn919553search2

Urgent `alert` semantics MUST NOT be used for routine:

- token updates;
- thinking state;
- progress;
- completed generation.

---

## 2.58 Completed responses SHOULD be discoverable without forced focus

Completion of a generated answer SHOULD NOT automatically move keyboard focus into the response unless that context change is required.

The interface SHOULD:

- announce completion appropriately;
- provide a stable way to navigate to the response.

A screen-reader user MUST NOT lose their composer position merely because generation completed.

---

## 2.59 Conversation semantics

Conversation interfaces SHOULD expose coherent semantic structure.

Each turn SHOULD make it possible to determine:

- author or role;
- content;
- relevant controls.

Repeated decorative labels SHOULD not create excessive screen-reader verbosity.

A generated response SHOULD be navigable using semantic headings, landmarks, message grouping, or another appropriate structure.

---

## 2.60 Generated content MUST preserve semantic markup

When generated content contains:

- headings;
- paragraphs;
- lists;
- tables;
- code;
- quotations

the rendered result SHOULD use the corresponding semantic HTML.

Visual Markdown styling without semantic elements MUST NOT be the standard rendering approach.

Heading levels SHOULD fit the surrounding document hierarchy rather than blindly reproducing model-provided heading numbers.

---

## 2.61 Generated tables MUST remain accessible

Generated tables MUST use semantic table markup where they represent tabular relationships.

Tables MUST NOT be rendered as images or monospaced ASCII solely because the model emitted text in that form when structured rendering is available.

Large generated tables SHOULD provide:

- horizontal accessibility strategy;
- responsive handling;
- downloadable structured data where useful.

---

## 2.62 Generated code MUST remain operable

Code blocks SHOULD expose:

- language where known;
- copy control;
- horizontal scrolling where necessary.

Copy controls MUST have accessible names.

Code highlighting MUST NOT reduce text contrast below Accessibility requirements.

Screen-reader users MUST be able to reach code without navigating decorative token spans individually.

---

## 2.63 Generated mathematics requires semantic access

Mathematical output SHOULD use an accessible math rendering strategy when supported.

Important equations MUST NOT exist only as raster images.

Generated explanations SHOULD provide textual context for complex notation where needed.

---

## 2.64 Generated images require accessible treatment

AI-generated images MUST follow the corpus image accessibility standard.

Where an image conveys meaningful content, appropriate alternative text or another equivalent representation MUST be available.

The alt text SHOULD describe the useful content, not merely:

`AI-generated image`.

AI provenance MAY be communicated separately.

---

## 2.65 Citations MUST remain accessible inside generated content

Interactive citation controls MUST not disrupt reading order.

Citation markers SHOULD remain compact visually while exposing descriptive accessible names.

Opening citation details MUST follow Overlay standards for:

- focus;
- dismissal;
- keyboard access.

---

## 2.66 Copy behavior MUST be predictable

Users SHOULD be able to copy generated output without accidentally copying:

- hidden status messages;
- control labels;
- citation implementation metadata;
- invisible accessibility text unrelated to the copied artifact.

Where citations are copied, the product SHOULD define whether the copied result includes:

- inline citation markers;
- source list;
- links.

---

## 2.67 Editing generated content

Generated content intended for downstream use SHOULD be editable where the workflow permits.

Users MUST be able to distinguish:

- regenerated content;
- manually edited content

where that distinction matters for audit or collaboration.

Regeneration MUST NOT overwrite manual edits without warning.

---

## 2.68 AI-generated form suggestions

AI suggestions in forms MUST remain suggestions until accepted when automatic application could materially change user intent.

Suggested values SHOULD be visually distinguishable before acceptance.

Acceptance MUST produce ordinary validated form state.

Rejecting a suggestion MUST NOT repeatedly reinsert it without a new trigger.

---

## 2.69 Autocomplete and inline generation

Inline AI completion MUST NOT interfere with ordinary text editing.

Suggested text SHOULD be distinguishable from committed text.

Users MUST have predictable controls to:

- accept;
- ignore;
- dismiss.

Screen readers MUST NOT repeatedly announce long speculative completions during ordinary typing.

---

## 2.70 Loading personality

AI loading states SHOULD be calm and factual.

Loading copy MAY communicate the current operation.

The product SHOULD NOT use fabricated activity such as:

- `Checking every possibility…`;
- `Almost done!`

unless that statement reflects actual system state.

Personality MUST NOT compromise status accuracy.

---

## 2.71 Latency messaging

A long-running request SHOULD provide meaningful state rather than an indefinitely animated spinner.

If execution duration becomes unusual, the product SHOULD communicate:

- that work is still active;
- relevant phase where known;
- cancellation options.

The product MUST NOT provide invented completion-time estimates.

---

## 2.72 Background or asynchronous execution

If the product genuinely supports background execution, the UI MUST distinguish:

- active foreground generation;
- queued work;
- background task;
- completed task.

A system that cannot continue work after the current interaction MUST NOT claim that it will complete something later.

Notification semantics MUST reflect actual background infrastructure.

---

## 2.73 Empty state

An AI surface empty state SHOULD explain:

- what the system can help with;
- what input is expected;
- important capability boundaries where useful.

Empty-state suggestions SHOULD be representative prompts, not claims that all shown tasks are guaranteed to succeed.

Sensitive information SHOULD NOT be solicited casually through example prompts.

---

## 2.74 Prompt input

The prompt composer is a form and MUST follow Forms & Validation.

It MUST support:

- keyboard input;
- multiline input where appropriate;
- predictable submission;
- accessible label.

Submission shortcuts MUST NOT make multiline authoring inaccessible.

The product MUST clearly distinguish:

- Enter to submit;
- Shift+Enter or equivalent to insert a new line

where keyboard conventions depend on that distinction.

---

## 2.75 Attachments

Attachment state MUST be explicit.

Users SHOULD be able to determine whether a file is:

- selected;
- uploading;
- uploaded;
- processed;
- failed.

The model MUST NOT imply it read an attachment that failed processing.

Removing an attachment before submission MUST remove it from the generation context.

---

## 2.76 File processing status

For long document-processing operations, the interface SHOULD distinguish:

- upload;
- parsing/indexing;
- ready;
- failure.

`Uploaded` MUST NOT be treated as equivalent to `available to the model` unless that is actually true.

---

## 2.77 Source and context boundaries

When a response uses a constrained source set, the UI SHOULD communicate that context where it affects interpretation.

Examples include:

- `Answering from uploaded files`;
- `Using company knowledge base`;
- `Web sources enabled`.

The system MUST NOT imply comprehensive external research when it used only a narrow context.

---

## 2.78 Conversation context limits

If earlier content is no longer available to the model because of architectural context limits, the product SHOULD avoid implying perfect recall.

Where loss of earlier context materially affects the task, the interface SHOULD communicate or mitigate it.

The system MUST NOT invent recollection of content that is no longer accessible.

---

## 2.79 User feedback

Feedback controls MAY collect quality signals such as:

- helpful;
- not helpful;
- incorrect citation;
- unsafe;
- formatting problem.

Feedback MUST NOT interrupt normal reading.

Feedback categories SHOULD be actionable.

Submitting feedback MUST follow applicable privacy and telemetry standards.

---

## 2.80 shadcn/ui baseline

shadcn/ui MUST be the component baseline for AI application UI.

Current shadcn/ui includes conventional primitives as well as message-oriented components such as `Message`, `Message Scroller`, `Bubble`, `Attachment`, plus `Progress`, `Skeleton`, `Alert`, `Tooltip`, `Textarea`, and related primitives. citeturn324584search4

Preferred mappings include:

| Concern | shadcn/ui baseline |
|---|---|
| Prompt input | `Textarea`, `Input Group` |
| Primary actions | `Button`, `Button Group` |
| Conversation message | `Message` / application message abstraction |
| Scrollable conversation | `Message Scroller` or canonical scroll pattern |
| Attachments | `Attachment` / application attachment abstraction |
| Processing state | `Spinner`, `Progress`, `Skeleton` as appropriate |
| Error or warning | `Alert` |
| Citation preview | `Popover`, `Hover Card`, `Sheet` depending complexity |
| Details / reasoning summary | `Collapsible`, `Accordion` |
| Memory/settings controls | `Dialog`, `Sheet`, standard form controls |
| Model selection | `Select`, `Combobox`, `Dropdown Menu` |
| Cost explanation | `Tooltip`, `Popover` for supplementary detail |
| Retry/regenerate/stop | `Button`, `Button Group` |

shadcn/ui `Progress` supports labelled progress composition, while `Skeleton` is explicitly intended as a loading placeholder. citeturn324584search0turn324584search5

Product teams SHOULD build AI-specific abstractions from these primitives rather than introduce an unrelated component system.

---

## 2.81 Design tokens

AI UX MUST use shared semantic tokens.

Relevant concepts SHOULD include:

- AI-generated content;
- user content;
- source/citation;
- pending;
- success;
- warning;
- error;
- refused;
- selected;
- uncertain;
- memory/personalization indicator where visually required.

Tokens MUST describe semantic purpose rather than model vendor or literal colour.

Prefer:

`--ai-source`

over:

`--ai-purple`.

AI identity colour MUST NOT override established semantic warning, destructive, or success colours.

---

## 2.82 AI styling MUST NOT imply authority

Generated responses MUST NOT use visual styling that makes them indistinguishable from:

- legal system notices;
- verified database records;
- official human approval;
- validated medical or financial results

unless the underlying content actually has that status.

Typography, badges, and colour SHOULD preserve the distinction between generated advice and authoritative application state.

---

## 2.83 Security state overrides generated content

If authorization changes, restricted generated or retrieved content MUST be removed or protected according to Security policy.

A generated response MUST NOT retain access to restricted source content merely because the response is already visible in client state where policy requires revocation.

Caches and conversation persistence MUST respect authorization boundaries.

---

## 2.84 Sensitive output handling

Generated output containing sensitive information MUST follow the same:

- access controls;
- copy controls where applicable;
- retention;
- export;
- audit

requirements as equivalent non-AI content.

Generated content MUST NOT be assumed non-sensitive simply because the model created it.

---

## 2.85 Auditability for consequential workflows

Where AI participates in consequential business workflows, systems SHOULD preserve sufficient provenance to reconstruct:

- user instruction;
- relevant model/version class where required;
- source context;
- generated proposal;
- user approval;
- tool action;
- resulting system response.

Audit logging MUST follow Security and privacy requirements and MUST NOT indiscriminately record hidden reasoning or secrets.

---

## 2.86 Testing

AI UX tests MUST cover more than ideal completed responses.

Representative test states SHOULD include:

- immediate completion;
- slow first token;
- streaming;
- stop;
- stream interruption;
- malformed structured output;
- refusal;
- rate limit;
- model error;
- tool failure;
- citation unavailable;
- contradictory sources;
- attachment processing failure;
- memory disabled;
- cost exhaustion;
- reduced-motion mode;
- keyboard-only use;
- screen-reader use.

The UI MUST be tested with very long generated content and very short content.

---

## 2.87 Accessibility testing

Accessibility testing MUST include:

- composer operation;
- send/stop transition;
- generation status;
- completed-message discovery;
- citation navigation;
- regenerated-version navigation;
- errors;
- refusal;
- code;
- tables;
- tool status.

Streaming MUST be tested with actual assistive technology.

Automated accessibility tests alone are insufficient to validate streaming announcement cadence.

# 3. Anti-patterns

The following are non-conforming unless an explicit, documented requirement provides a stronger justification.

## 3.1 Disclosure

- AI-generated content presented as human-authored without disclosure.
- Sparkle icon as the only AI disclosure.
- Generated database-like values styled as verified truth.
- Assistant persona implying a real employee performed work when it did not.

## 3.2 Streaming

- Treating a partially streamed answer as complete.
- Announcing every streamed token to a screen reader.
- Controls moving continuously as tokens arrive.
- Losing all useful partial output after connection interruption.
- Streaming malformed Markdown protocol directly to users.
- Auto-scrolling so aggressively that users cannot inspect earlier text.

## 3.3 Thinking and progress

- Exposing raw private chain-of-thought.
- Fabricating detailed “thinking” narration.
- Fake percentages.
- `Almost done` without actual progress knowledge.
- Treating model-generated progress prose as execution telemetry.
- Showing verbose internal logs to ordinary users without purpose.

## 3.4 Sources

- Citation numbers with no source behind them.
- One source list implying all claims are supported.
- Cited styling implying guaranteed truth.
- Fabricated titles, URLs, or document references.
- Quote styling for model paraphrase.
- Source previews inaccessible to keyboard users.

## 3.5 Confidence

- Arbitrary `97% confident` labels.
- Green confidence badge meaning “true”.
- Generic uncertainty disclaimers on every message.
- Hiding known uncertainty because the output reads more confidently.
- Treating disagreement between sources as model confidence.

## 3.6 Regeneration and editing

- Regeneration silently deleting the previous answer.
- Retrying a failed external action without checking whether it already succeeded.
- Editing an old prompt while leaving dependent later messages presented as valid.
- Regeneration duplicating sent emails, purchases, deletions, or other effects.

## 3.7 Memory

- Saying `I'll remember that` without successful persistence.
- Saying information was deleted without actual deletion state.
- Calling connected email or document access “memory”.
- Hiding persistent personalization so users cannot understand why it affects answers.
- Persisting sensitive context unnecessarily.

## 3.8 Errors and refusals

- Refusal displayed as `Something went wrong`.
- Rate limit displayed as safety refusal.
- Tool authorization failure blamed on the model.
- Clearing the user's prompt after a generation error.
- Recommending repeated retries for an intentionally unsupported request.
- Hostile or moralizing refusal language.

## 3.9 Cost and quota

- Charging material credits without pre-action visibility.
- Calling an estimate an exact price.
- Requiring users to understand token accounting when credits/currency would be clearer.
- Running expensive agents indefinitely without budget controls.
- Quota exhaustion displayed as generic model failure.

## 3.10 Actions

- Generated `Done` text when the API action failed.
- A model granting itself permission to perform an action.
- Hidden bundles of consequential tool calls behind one vague confirmation.
- Automatically navigating to model-generated external links.
- Executing AI-suggested destructive action without required authorization.

## 3.11 Accessibility

- Token-by-token `aria-live` announcements.
- AI answer rendered as one giant unstructured text node.
- Citation controls named only `1`, `2`, `3`.
- Code copy control with no accessible name.
- Streaming completion stealing focus from the composer.
- AI suggestions appearing only through colour.
- Generated images without equivalent alternatives where needed.

## 3.12 Loading personality

- Fake status messages to entertain users.
- Anthropomorphic processing statements presented as technical facts.
- Artificially delaying output so an animation can finish.
- Endless spinner where actual tool state is available.

## 3.13 Security

- Treating retrieved text as trusted system instruction.
- Prompt content bypassing backend authorization.
- Exposing secrets in generation debug UI.
- Recording private reasoning or sensitive prompts indiscriminately for analytics.
- Assuming generated content is harmless because it originated from the model.

# 4. Checklist

## 4.1 AI disclosure

- [ ] Users can determine that AI is involved.
- [ ] Generated and authoritative application content remain distinguishable.
- [ ] Disclosure does not rely only on colour or iconography.
- [ ] The product does not falsely imply human review or action.

## 4.2 Streaming

- [ ] Pending, streaming, complete, stopped, and failed states are distinct.
- [ ] Streaming remains readable.
- [ ] Partial content can be recovered where appropriate.
- [ ] Stop is accessible and stable.
- [ ] Visual streaming does not produce token-by-token AT announcements.
- [ ] Stream failures do not masquerade as completion.

## 4.3 Progress and thinking

- [ ] User-visible progress reflects real system/task state.
- [ ] Unknown progress is represented as indeterminate.
- [ ] No fabricated percentages are shown.
- [ ] Raw private chain-of-thought is not exposed.
- [ ] Useful explanation is provided through summaries, methodology, assumptions, or sources instead.
- [ ] Tool progress derives from orchestration state where available.

## 4.4 Citations

- [ ] Citations are attached to the claims they support.
- [ ] Every citation resolves to a real source object.
- [ ] Source identity is clear.
- [ ] Access restrictions are represented accurately.
- [ ] Quotes and paraphrases are distinguishable.
- [ ] Citation controls are keyboard and screen-reader accessible.
- [ ] Citation styling does not imply guaranteed correctness.

## 4.5 Uncertainty

- [ ] Material uncertainty is communicated.
- [ ] Uncertainty appears near the relevant claim.
- [ ] Missing data, disagreement, estimate, and prediction are distinguished where relevant.
- [ ] Unsupported numerical confidence is absent.
- [ ] Visual certainty indicators have validated semantics.

## 4.6 User controls

- [ ] Stop is available for materially long generation.
- [ ] Retry and regenerate have distinct semantics.
- [ ] Regeneration does not silently destroy previous output.
- [ ] Historical edits preserve or clearly revise conversational lineage.
- [ ] Consequential actions are not repeated during regeneration.

## 4.7 Memory

- [ ] Conversation context and persistent memory are distinguishable.
- [ ] Persistent memory is inspectable where supported.
- [ ] Memory enable/disable/update/delete actions reflect actual state.
- [ ] Connected sources are not misrepresented as memory.
- [ ] Sensitive memory follows Security and privacy requirements.

## 4.8 Errors and refusals

- [ ] Technical errors, refusals, limits, and authorization failures are distinct.
- [ ] User work is preserved after recoverable errors.
- [ ] The next available action is clear.
- [ ] Refusal wording is concise and non-accusatory.
- [ ] Retry cannot accidentally duplicate external actions.

## 4.9 Cost and quota

- [ ] Material cost is visible before commitment.
- [ ] Estimates are identified as estimates.
- [ ] Remaining quota/credits are understandable where applicable.
- [ ] Expensive long-running tasks have appropriate limits.
- [ ] Quota exhaustion has a distinct state.

## 4.10 External actions

- [ ] Suggestion, draft, approval, execution, and completion are distinct.
- [ ] Tool/API state is authoritative.
- [ ] Consequential actions have appropriate confirmation.
- [ ] Authorization is enforced independently of model output.
- [ ] Tool failures cannot become fabricated success messages.

## 4.11 Forms and generated data

- [ ] Generated structured values pass normal validation.
- [ ] AI suggestions remain suggestions until accepted where necessary.
- [ ] Generated edits do not bypass authorization or domain constraints.
- [ ] Form error state survives generation and retries.

## 4.12 Accessibility

- [ ] Composer and generation controls are keyboard operable.
- [ ] Generation status is programmatically available.
- [ ] Streaming announcements are appropriately throttled.
- [ ] Completion does not unexpectedly steal focus.
- [ ] Generated headings use semantic hierarchy.
- [ ] Tables use semantic table markup.
- [ ] Code blocks are usable and copy controls are labelled.
- [ ] Citations have descriptive accessible names.
- [ ] Generated images have appropriate alternatives.
- [ ] AI suggestions are not distinguished by colour alone.

## 4.13 Security

- [ ] Retrieved content is treated as untrusted input.
- [ ] Prompt text cannot override backend authorization.
- [ ] Sensitive data is protected in history, logs, and generated content.
- [ ] Generated links follow safe-link policy.
- [ ] AI output cannot self-authorize tool use.
- [ ] Audit records do not indiscriminately expose secrets or hidden reasoning.

## 4.14 State management

- [ ] Conversation branches have explicit lineage.
- [ ] Generation state has one canonical owner.
- [ ] Partial output state is represented explicitly.
- [ ] External actions remain independent from conversational branch presentation.
- [ ] Memory state reflects backend state.
- [ ] Animation state is not confused with generation state.

## 4.15 shadcn/ui

- [ ] shadcn/ui remains the component baseline.
- [ ] Composer uses established input primitives.
- [ ] Status and errors use canonical components.
- [ ] Citation details use accessible overlay components.
- [ ] Progress uses `Progress`, `Spinner`, `Skeleton`, or an appropriate composition.
- [ ] AI-specific abstractions extend rather than replace the component system.

## 4.16 Testing

- [ ] Slow first-token latency is tested.
- [ ] Streaming interruption is tested.
- [ ] Stop is tested.
- [ ] Retry is tested.
- [ ] Regeneration is tested.
- [ ] Refusal is tested.
- [ ] Tool failure is tested.
- [ ] Citation failure is tested.
- [ ] Memory state changes are tested.
- [ ] Quota exhaustion is tested.
- [ ] Long generated content is tested.
- [ ] Keyboard and screen-reader flows are tested with actual streaming.

## 4.17 Corpus alignment

- [ ] Security controls authorization and untrusted source handling.
- [ ] Data & Database controls persistence, provenance and retention.
- [ ] API controls streaming, cancellation, retries, limits and tool execution.
- [ ] State Management controls branches, generation state and memory state.
- [ ] Forms & Validation governs prompt inputs and AI-generated structured values.
- [ ] Accessibility governs streaming status and generated-content semantics.

# 5. Canonical summary

A Gold Standard 2026 AI interface MUST make AI involvement understandable without overwhelming the user with repetitive disclaimers.

Streaming MUST be represented as partial generation rather than finished truth. Pending, streaming, stopped, failed, refused, and completed states MUST remain distinguishable.

Users SHOULD be able to stop materially long generation. Retry, regenerate, edit, and continue MUST have distinct semantics, and regeneration MUST NOT silently destroy previous useful output or repeat consequential external actions.

Progress disclosure MUST represent actual system state. Unknown progress MUST remain indeterminate, and products MUST NOT fabricate percentages or detailed internal activity merely to appear transparent.

Raw private chain-of-thought MUST NOT be treated as a standard user-visible surface. Useful transparency SHOULD instead come from concise reasoning summaries, assumptions, methodology, evidence, tool status, and verifiable intermediate results. citeturn919553search0turn919553search3

Citations MUST point to real sources and SHOULD sit near supported claims. Citation presence MUST NOT be presented as proof that every generated statement is correct.

Material uncertainty SHOULD be communicated specifically and locally. Unsupported numerical confidence MUST NOT be invented.

Persistent memory, current conversation context, account preferences, and connected-source access MUST remain conceptually distinct. Any claim that information was remembered, deleted, or changed MUST reflect actual persistence state.

Generated language describing an external action MUST never override authoritative API state. The interface MUST distinguish suggestion, draft, approval, execution, and successful completion.

Technical errors, refusals, authorization failures, rate limits, and quota exhaustion MUST remain distinguishable. Recoverable failures SHOULD preserve user input and useful partial output.

Material AI cost or credit usage SHOULD be visible before commitment. Estimated and actual cost MUST remain distinct.

Generated structured values MUST pass the same validation and authorization requirements as ordinary user input. Model output MUST NOT bypass Security, Forms, API, or database invariants.

AI-generated content MUST be accessible as semantic content rather than merely visually formatted text. Streaming status MUST be available to assistive technology without creating token-by-token announcement noise; W3C requires programmatic status communication and explicitly cautions that excessive live updates can become overly chatty. citeturn919553search1turn919553search5

shadcn/ui is the canonical component baseline. AI-specific message, composer, citation, source, generation-state, and memory abstractions SHOULD compose the shared component system rather than create a parallel one. citeturn324584search4

**Canonical rule:** an AI interaction is conforming only when users can understand what is generated, what is sourced, what is uncertain, what is remembered, what is happening, what has actually been executed, what it may cost, and how to stop, correct, inspect, or recover the interaction without relying on hidden model reasoning or inaccessible interface state.

The strictest architectural boundary in this standard is deliberate: **model language is presentation; application/tool state is authority**. That prevents a large class of AI UX failures around fake progress, fabricated action completion, memory claims, citations, and cost reporting.
