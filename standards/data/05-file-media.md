# File & Media Guidelines — Gold Standard 2026

## 1. Purpose

These guidelines define the canonical organizational standard for:

- file uploads;
- image uploads;
- video uploads;
- audio uploads;
- documents;
- archives;
- attachments;
- direct-to-object-storage uploads;
- MIME verification;
- extension validation;
- content sniffing;
- size limits;
- image dimensions;
- media duration;
- decompression;
- filename handling;
- object storage;
- object keys;
- signed URLs;
- public/private delivery;
- CDN delivery;
- thumbnails;
- image transformation;
- video transcoding;
- metadata extraction;
- metadata stripping;
- EXIF handling;
- malware scanning;
- antivirus;
- sandboxing;
- content disarm and reconstruction;
- quarantine;
- moderation;
- retention;
- deletion;
- legal holds;
- recovery;
- observability;
- privacy;
- authorization.

The objective is to ensure uploaded and generated files are:

```text
Validated
Authorized
Contained
Non-executable by default
Scanned where required
Privacy-aware
Tenant-safe
Recoverable where required
Disposable when expired
Efficiently deliverable
```

The core principle is:

> **Every uploaded file is untrusted input until its type, size, ownership, storage destination, processing requirements, and security state have been independently established by trusted server-side controls.**

---

# 2. Normative Language

- **MUST** — mandatory.
- **MUST NOT** — prohibited.
- **SHOULD** — expected unless justified.
- **SHOULD NOT** — generally avoided unless justified.
- **MAY** — optional.

Exceptions SHOULD document:

```text
Reason
File/media class
Threat model
Privacy impact
Storage impact
Compensating controls
Owner
Review date
```

---

# 3. File Upload Is an Untrusted-Input Boundary

A file upload is not:

```text
just a blob
```

It may contain:

```text
malware
scripts
active content
parser exploits
decompression bombs
metadata
sensitive information
misleading MIME declarations
unexpected embedded formats
```

Treat uploads with the same rigor as any other untrusted input.

---

# 4. Upload Architecture

Canonical pipeline:

```text
Authorize upload
↓
Issue constrained upload destination
↓
Receive object
↓
Quarantine
↓
Validate size/type/content
↓
Scan/process
↓
Normalize/transform
↓
Mark accepted
↓
Publish/make retrievable
```

Uploads SHOULD NOT become generally retrievable before required validation is complete.

---

# 5. Upload States

A file lifecycle SHOULD distinguish states such as:

```text
initiated
uploading
uploaded
validating
quarantined
processing
accepted
rejected
available
deleted
expired
```

Do not represent every state as a single ambiguous:

```text
uploaded = true
```

---

# 6. Upload Intent

A server SHOULD create upload intent before accepting important files.

The intent MAY define:

```text
owner
tenant
purpose
allowed types
maximum size
destination
expiry
```

---

# 7. Upload Authorization

Only authorized actors may request or complete uploads.

---

# 8. Upload Permission

Authorization SHOULD answer:

```text
Can this actor attach a file to this resource?
```

not merely:

```text
Is this actor logged in?
```

---

# 9. Attachment Authorization

If uploading to:

```text
project P
invoice I
ticket T
```

the uploader MUST be authorized for that resource.

---

# 10. Object Key Does Not Grant Authorization

Knowing:

```text
bucket/path/object-id
```

MUST NOT by itself grant access.

---

# 11. Direct Upload

Large files SHOULD often upload directly from the client to object storage using constrained server-authorized upload credentials.

This avoids routing all file bytes through application servers.

---

# 12. Direct Upload Does Not Bypass Validation

Direct-to-storage upload changes transport architecture.

It does not eliminate:

```text
authorization
validation
scanning
quarantine
processing
retention
```

requirements.

---

# 13. Upload Destination

Direct uploads SHOULD target:

```text
quarantine/pending namespace
```

rather than final public storage.

---

# 14. Server-Generated Object Key

Object keys MUST normally be generated by the trusted application.

Do not allow arbitrary client-supplied storage paths.

---

# 15. Original Filename

The original user filename MAY be retained as metadata for display.

It SHOULD NOT normally become the storage key.

---

# 16. Filename Is Untrusted

Treat filenames as untrusted text.

They may contain:

```text
path separators
control characters
Unicode tricks
HTML
shell characters
very long strings
```

---

# 17. Path Traversal

File names/paths MUST NOT permit traversal such as:

```text
../../etc/passwd
```

---

# 18. Storage Path

Storage location MUST be derived by the application, not concatenated directly from user filenames.

---

# 19. Filename Length

Original/display filenames SHOULD have a defined maximum length.

---

# 20. Filename Normalization

Display filenames SHOULD be normalized to a safe Unicode form and sanitized for the output context.

---

# 21. Preserve Useful Name

Do not destroy the user's meaningful filename unnecessarily.

Store separately:

```text
storage object key
display/original filename
```

---

# 22. File Extension

File extension is one signal.

It is NOT authoritative proof of type.

---

# 23. Extension Allowlist

Upload features SHOULD allow only file extensions required by the business function.

---

# 24. Denylist Is Insufficient

Do not attempt security primarily through:

```text
block .exe
block .php
block .jsp
...
```

Use a positive allowlist.

---

# 25. Extension Parsing

Extension validation MUST account for:

```text
multiple dots
mixed case
trailing spaces/dots
Unicode lookalikes
encoded filenames
```

---

# 26. Double Extension

Files such as:

```text
invoice.pdf.exe
photo.jpg.php
```

MUST NOT bypass type validation.

---

# 27. MIME Header

The client-provided:

```text
Content-Type
```

MUST NOT be trusted as proof of file type.

---

# 28. Content Verification

The server or trusted processing pipeline MUST verify that file content corresponds to the allowed file type.

---

# 29. Type Verification Layers

Verification SHOULD combine appropriate signals:

```text
extension
declared MIME
magic bytes/signature
parser validation
format-specific decoding
rewriting/transcoding
```

depending on risk.

---

# 30. Magic Bytes

Magic-byte detection is useful but not sufficient for every format.

Polyglot and malformed files may still require deeper validation.

---

# 31. Parser Validation

For complex formats, use a format-aware parser/decoder to verify structural validity.

---

# 32. Decoding as Validation

For images, successfully decoding and rewriting the image can provide stronger validation than trusting headers alone.

---

# 33. MIME Canonicalization

After trusted detection, the application SHOULD assign a canonical MIME type.

---

# 34. Extension Canonicalization

Stored/output extension SHOULD match the accepted canonical type when an extension is used.

---

# 35. MIME Mismatch

If:

```text
extension = .jpg
content = PDF
```

the upload SHOULD normally be rejected rather than guessed into acceptance.

---

# 36. Ambiguous Formats

Ambiguous or polyglot content SHOULD be rejected unless the application has an explicit safe handling strategy.

---

# 37. Allowed Types Are Feature-Specific

Do not create one global:

```text
all uploads support every allowed file type
```

policy.

Example:

```text
avatar
→ JPEG/PNG/WebP

contract attachment
→ PDF

data import
→ CSV
```

---

# 38. High-Risk Formats

Formats capable of containing:

```text
macros
scripts
embedded files
external references
active content
```

require stronger review.

---

# 39. Executable Files

User-uploaded executable/script content SHOULD NOT be accepted unless execution is an explicit business requirement with strong sandboxing.

---

# 40. HTML/SVG

HTML and SVG can contain active content.

They MUST NOT be treated as equivalent to passive raster images.

---

# 41. SVG Policy

If SVG upload is permitted:

```text
sanitize aggressively
or
rasterize/transform
```

before display when appropriate.

---

# 42. Office Documents

Office/document formats capable of macros or embedded objects SHOULD receive scanning and/or content disarm controls appropriate to the threat model.

---

# 43. PDF

PDF is a complex active-capable document format.

Do not treat:

```text
application/pdf
```

as inherently safe.

---

# 44. Archives

ZIP/TAR and similar archives require additional validation.

---

# 45. Archive Expansion

Before extraction, the system SHOULD enforce:

```text
compressed size
estimated/uncompressed size
file count
nesting depth
path safety
compression ratio
```

limits.

---

# 46. Zip Bomb

A tiny compressed archive expanding to enormous data MUST NOT exhaust:

```text
disk
memory
CPU
```

---

# 47. Nested Archive

Nested archives SHOULD have a maximum recursion depth.

---

# 48. Archive Path Traversal

Archive extraction MUST defend against entries such as:

```text
../../outside
```

---

# 49. Symlink Extraction

Archive extraction SHOULD reject or tightly control symbolic/hard links.

---

# 50. Extraction Root

All extracted content MUST remain within a controlled destination.

---

# 51. File Count

Uploads that can contain many files MUST have an entry-count limit.

---

# 52. Size Limits

Every upload endpoint MUST define a maximum accepted size.

---

# 53. Size Limit Is Product-Specific

Examples:

```text
avatar
→ small

PDF attachment
→ medium

4K source video
→ large
```

Do not reuse arbitrary global defaults.

---

# 54. Multi-Layer Size Limits

Size limits SHOULD align across:

```text
browser/client
edge/CDN
load balancer
application
signed upload policy
object storage
processing worker
```

---

# 55. Early Rejection

Reject oversized uploads as early as possible.

---

# 56. Declared Size

Client-declared size MAY support preflight UX.

It MUST NOT be trusted as the only enforcement.

---

# 57. Actual Size

Validate actual stored/uploaded object size before acceptance.

---

# 58. Chunked Upload

Chunked/resumable uploads MUST still enforce a final total size.

---

# 59. Multipart Upload

Abandoned multipart uploads SHOULD be automatically cleaned up.

---

# 60. Storage Quota

Users/tenants SHOULD have storage quotas where unbounded uploads could create cost or abuse risk.

---

# 61. Upload Rate Limit

Upload creation SHOULD be rate-limited according to abuse/cost risk.

---

# 62. Dimension Limits

Images SHOULD have maximum decoded dimensions.

---

# 63. Pixel Bomb

A compressed image with extreme dimensions can exhaust processing memory.

Control:

```text
width
height
total pixels
```

---

# 64. Image Aspect Ratio

Extreme aspect ratios MAY be rejected when downstream processing cannot safely handle them.

---

# 65. Video Constraints

Video upload policies MAY enforce:

```text
container
codec
resolution
duration
frame rate
bitrate
```

according to product requirements.

---

# 66. Audio Constraints

Audio policies MAY enforce:

```text
container
codec
duration
sample rate
channels
bitrate
```

---

# 67. Media Probe

Use a trusted media parser/probe rather than only filename/MIME headers.

---

# 68. Media Duration

Long-duration media SHOULD be bounded where processing/storage cost matters.

---

# 69. Processing Budget

Every accepted media class SHOULD fit within bounded:

```text
CPU
memory
processing time
disk
```

limits.

---

# 70. Processing Timeout

Media/document processing jobs MUST have execution timeouts.

---

# 71. Sandbox Processing

High-risk parsers SHOULD run in isolated/sandboxed environments where practical.

---

# 72. Least-Privilege Processor

Media-processing workers SHOULD have only required:

```text
read source
write derived output
write status
```

permissions.

---

# 73. Parser Isolation

A compromised parser SHOULD NOT automatically gain:

```text
database admin
cloud admin
secret access
unrestricted network
```

---

# 74. Network Egress

File processors SHOULD have restricted network egress where file contents do not legitimately need external network access.

---

# 75. SSRF Through Documents

Some document/media parsers may follow external references.

Network policy SHOULD prevent unsafe server-side fetch behavior.

---

# 76. Temporary Files

Processing temporary files MUST use controlled directories and bounded storage.

---

# 77. Temporary File Cleanup

Temporary processing files MUST be removed after:

```text
success
failure
timeout
```

where safe.

---

# 78. Local Disk Is Not Durable Storage

Do not treat container/server temporary disk as authoritative file storage.

---

# 79. Object Storage Default

Durable uploaded blobs SHOULD normally live in managed object storage or another dedicated blob store.

---

# 80. Database Blob Storage

Storing large binaries directly in a relational database SHOULD be justified by transactional or domain requirements.

Do not do it by default.

---

# 81. Object Storage Is Private by Default

Buckets/containers holding user files MUST default to private access unless public distribution is a deliberate requirement.

---

# 82. Public Bucket

A public bucket SHOULD NOT be the default mechanism for sharing user-generated files.

---

# 83. Public Media

Public media SHOULD preferably be published through:

```text
controlled public object namespace
CDN
public asset pipeline
```

rather than exposing all uploaded storage.

---

# 84. Storage Segmentation

Consider separate storage scopes for:

```text
pending/quarantine
private accepted
public accepted
derived media
temporary processing
```

---

# 85. Quarantine Storage

Pending files SHOULD remain inaccessible to normal users except through controlled status APIs until validated.

---

# 86. Object Key

Object keys SHOULD use opaque stable identifiers.

Example:

```text
tenant/t_42/files/f_01J...
```

rather than:

```text
tenant/t_42/files/passport-john-smith.pdf
```

---

# 87. PII in Object Keys

Avoid unnecessary PII in object keys because object names may appear in:

```text
logs
audit events
CDN records
storage inventory
```

---

# 88. Tenant Scope

Object metadata/records MUST associate the file with its authoritative tenant.

---

# 89. Storage Namespace

Tenant-specific paths MAY aid operations but MUST NOT replace authorization.

---

# 90. Object ID

Files SHOULD have an application-level stable ID independent of provider object path.

---

# 91. File Record

Important uploaded files SHOULD have a database/application metadata record.

Example:

```text
file_id
tenant_id
owner/resource
original_name
storage_key
size
canonical_mime
status
checksum
created_at
retention_class
```

---

# 92. Metadata Record Is Authoritative

The application file record SHOULD govern:

```text
ownership
status
authorization
retention
```

rather than storage listing alone.

---

# 93. Object Existence Mismatch

Systems MUST tolerate cases where:

```text
DB record exists
object missing
```

or:

```text
object exists
DB record missing
```

through reconciliation/cleanup.

---

# 94. Upload Completion

A direct upload is not considered accepted merely because object storage confirms bytes exist.

---

# 95. Completion Verification

After direct upload, the server SHOULD verify:

```text
expected object key
actual size
checksum where applicable
content type
upload ownership/intent
```

before processing.

---

# 96. Upload Intent Expiry

Unused upload intents SHOULD expire.

---

# 97. Orphan Upload

Objects uploaded but never finalized SHOULD be automatically removed after a bounded interval.

---

# 98. Checksums

Upload flows SHOULD use content checksums where useful for:

```text
integrity
corruption detection
duplicate detection
```

---

# 99. Checksum Is Not Malware Detection

A checksum proves content identity/integrity relative to expected data.

It does not establish safety.

---

# 100. Content Hash

Cryptographic hashes MAY be stored for:

```text
integrity
deduplication
malware intelligence
```

where justified.

---

# 101. Deduplication

Content deduplication SHOULD be used cautiously.

---

# 102. Cross-Tenant Deduplication

Physical deduplication across tenants MUST NOT create:

```text
existence side channels
authorization bypass
retention coupling
```

---

# 103. User-Visible Deduplication

Do not reveal:

```text
someone else already uploaded this file
```

when that fact leaks cross-tenant/user information.

---

# 104. Signed URLs

Signed URLs MAY grant temporary direct access to private object storage.

---

# 105. Signed URL Is a Bearer Capability

Anyone possessing an unexpired signed URL may be able to use it according to the signature's granted operation.

Treat it accordingly.

---

# 106. Signed URL Scope

Signed URLs SHOULD be restricted to:

```text
one object
one operation
short lifetime
```

where possible.

---

# 107. Upload Signed URL

Upload URLs SHOULD authorize only the intended destination.

---

# 108. Download Signed URL

Download URLs SHOULD authorize only the intended private object.

---

# 109. Delete Signed URL

Client-side signed delete URLs SHOULD be avoided unless the product explicitly requires them.

Deletion is usually safer through the application API.

---

# 110. Short Expiry

Signed URL lifetime SHOULD be as short as practical for the user interaction.

---

# 111. Long-Lived Signed URL

Do not use multi-day/week signed URLs merely to avoid implementing proper access handling unless the use case genuinely requires them.

---

# 112. URL Logging

Signed URLs MAY contain sensitive authentication material.

They SHOULD NOT be logged in full.

---

# 113. Referrer Leakage

Design download pages to minimize unintended signed-URL leakage through:

```text
logs
analytics
referrers
support tools
```

---

# 114. Authorization Before Signing

The application MUST authorize the requester before issuing a signed read/download URL.

---

# 115. Upload Authorization Before Signing

Likewise, a client MUST be authorized before receiving a signed upload capability.

---

# 116. Signed URL Credential Scope

The identity used to sign URLs SHOULD have the minimum storage permissions required.

---

# 117. Public Link vs Signed Link

A long-lived public share link is a product capability, not merely a long-expiry signed URL.

It SHOULD have its own:

```text
share record
revocation
audit
expiry
authorization
```

model.

---

# 118. Revocation Limitation

Some signed URLs cannot be individually revoked easily before expiry without changing underlying policy/credentials.

Use short lifetimes where immediate revocation matters.

---

# 119. Stable Application URL

User-facing links MAY point to:

```text
/files/{file_id}
```

which re-authorizes and redirects/streams to a short-lived storage URL.

---

# 120. CDN Delivery

CDNs SHOULD be used for media where they improve:

```text
latency
bandwidth
origin protection
transformation delivery
```

---

# 121. CDN Does Not Authorize

Private-media authorization MUST remain deliberate.

Do not infer:

```text
CDN URL exists
→ user may access it
```

---

# 122. Private CDN

Private media MAY use:

```text
signed CDN URLs
signed cookies
application authorization gateway
```

depending on architecture.

---

# 123. Cache-Control

Media responses SHOULD define appropriate HTTP caching semantics.

---

# 124. Immutable Derived Asset

Content-addressed/versioned thumbnails can generally use long cache lifetimes.

---

# 125. Mutable Media URL

Do not long-cache a mutable URL unless invalidation/versioning is designed.

---

# 126. Content-Disposition

Download responses SHOULD set `Content-Disposition` appropriately.

---

# 127. Attachment Delivery

Potentially active/untrusted document formats SHOULD generally download as attachments rather than render inline.

---

# 128. Inline Display

Inline display SHOULD be limited to types intentionally supported for safe rendering.

---

# 129. Filename in Content-Disposition

Response filenames MUST be safely encoded.

Do not directly interpolate raw user filenames into headers.

---

# 130. Content-Type on Download

Serve the trusted canonical media type.

Do not merely echo the uploader's original MIME header.

---

# 131. `nosniff`

Responses serving user-controlled files SHOULD consider:

```text
X-Content-Type-Options: nosniff
```

where appropriate.

---

# 132. Active Content Origin Isolation

High-risk user-controlled content MAY be served from a separate origin/domain to isolate it from authenticated application cookies and origin privileges.

---

# 133. Cookie Isolation

A dedicated user-content origin SHOULD avoid receiving sensitive application cookies.

---

# 134. Content Security Policy

Inline-rendered user content SHOULD use restrictive browser security controls appropriate to the file type.

---

# 135. Thumbnail Generation

Images/videos SHOULD generally use server-generated trusted thumbnails rather than requiring clients to process huge originals.

---

# 136. Thumbnail Source

Generate thumbnails only after minimum file validation.

---

# 137. Thumbnail Rewriting

Image decoding and rewriting can remove unsupported/embedded payload data and normalize representation.

---

# 138. Thumbnail Dimensions

Define canonical thumbnail sizes.

Avoid generating every arbitrary requested dimension.

---

# 139. Transformation Explosion

Dynamic transformation endpoints MUST prevent unbounded variants.

Bad:

```text
?width=1
?width=2
...
?width=100000
```

creating limitless cached objects.

---

# 140. Transformation Allowlist

Prefer:

```text
avatar_small
avatar_medium
avatar_large
```

or bounded dimension policies.

---

# 141. Image Aspect Ratio

Thumbnailing SHOULD preserve or intentionally crop aspect ratio.

---

# 142. Crop Rules

Product-specific crop semantics SHOULD be deterministic.

---

# 143. Image Quality

Compression/quality SHOULD balance:

```text
visual fidelity
bandwidth
storage
processing cost
```

---

# 144. Modern Formats

Derived media MAY use:

```text
WebP
AVIF
```

or other supported formats where compatibility and processing justify them.

---

# 145. Preserve Original

Whether original media is retained MUST be explicit.

---

# 146. Original Retention

Keep originals when needed for:

```text
future transformations
download
legal record
quality preservation
```

---

# 147. Discard Original

Originals MAY be removed after normalized derivative creation when product/privacy requirements permit.

---

# 148. Derived Files

Derived media SHOULD reference its source file/version.

---

# 149. Derivative Invalidation

Replacing/deleting the source SHOULD define behavior for:

```text
thumbnails
transcodes
previews
cached variants
```

---

# 150. Media Versioning

New source versions SHOULD generally create new derived-object identities.

---

# 151. Video Transcoding

Video uploads SHOULD normally be transcoded into supported delivery formats rather than serving arbitrary uploaded codecs directly.

---

# 152. Video Processing

A transcoding pipeline SHOULD:

```text
probe
validate
transcode
generate thumbnails
record duration/dimensions
publish
```

---

# 153. Adaptive Streaming

Large video products MAY generate adaptive streaming variants.

---

# 154. Media Manifest

Streaming manifests are derived assets and inherit authorization requirements from the source media.

---

# 155. Segment Authorization

Private video segment delivery MUST remain protected.

Protecting only the manifest may be insufficient depending on CDN architecture.

---

# 156. Audio Processing

Audio MAY be normalized/transcoded into supported formats before delivery.

---

# 157. Document Preview

Document previews SHOULD be generated from processed content in isolated workers.

---

# 158. Preview Is Derived Content

A generated preview MUST inherit:

```text
tenant
authorization
retention
```

from its source.

---

# 159. OCR

OCR SHOULD be used only when required by the product.

OCR output becomes derived data with its own privacy/security implications.

---

# 160. Metadata

Files may contain metadata beyond the visible content.

Examples:

```text
EXIF
GPS
camera identifiers
author name
software versions
document history
timestamps
embedded thumbnails
```

---

# 161. Metadata Review

Every accepted file class SHOULD define which metadata is:

```text
needed
retained
stripped
exposed
```

---

# 162. Default Metadata Minimization

User-generated media SHOULD generally have unnecessary sensitive metadata removed from public derivatives.

---

# 163. GPS Metadata

Location metadata SHOULD NOT be exposed accidentally through public image delivery.

---

# 164. EXIF

EXIF SHOULD be stripped from public image derivatives unless a product feature requires it.

---

# 165. Orientation

If stripping EXIF, image orientation SHOULD first be normalized so the image still renders correctly.

---

# 166. Original Metadata

Private originals MAY retain metadata if required, but access and retention follow privacy policy.

---

# 167. Document Metadata

Generated/public documents SHOULD avoid leaking:

```text
internal username
filesystem path
author identity
revision history
hidden comments
```

unless intentional.

---

# 168. Metadata Extraction

Extract metadata using trusted libraries in a bounded processing environment.

---

# 169. Metadata Is Untrusted

Never render extracted metadata as trusted HTML or execute it.

---

# 170. Malware Scanning

Malware scanning SHOULD be applied according to file type, threat model, audience, and processing path.

---

# 171. When Scanning Is Strongly Expected

Scanning is especially important for:

```text
documents
archives
shared attachments
enterprise collaboration
publicly redistributed uploads
files opened by staff
```

---

# 172. Images Still Need Validation

Even if antivirus scanning is not used for every simple image upload, images still require trusted decoding/rewriting and bounded processing.

---

# 173. Scan Before Publication

Files requiring malware scanning SHOULD remain quarantined until scanning succeeds.

---

# 174. Scan Status

The metadata record SHOULD distinguish:

```text
pending
clean
malicious
scan_failed
unsupported
```

---

# 175. Scan Failure

A scanner outage MUST NOT be interpreted as:

```text
file is clean
```

---

# 176. Fail-Safe Policy

For file classes requiring scanning:

```text
scanner unavailable
→ file remains unavailable/quarantined
```

unless an explicitly reviewed fallback exists.

---

# 177. Scanner Timeout

Scanning MUST have bounded timeouts.

---

# 178. Scanner Retry

Temporary scanner failures MAY use bounded retries.

---

# 179. Malicious Detection

Detected malicious files SHOULD be:

```text
quarantined/deleted according to policy
blocked from retrieval
recorded for audit/security analysis
```

---

# 180. User Response

User-facing errors SHOULD not reveal unnecessary malware-detection internals.

---

# 181. Security Notification

Repeated malicious upload attempts MAY trigger abuse/security investigation.

---

# 182. Public Malware-Scanning Services

Do not upload private/customer files to third-party public scanning services without privacy/vendor approval.

---

# 183. Malware Hash Lookup

Hash reputation MAY supplement scanning but cannot safely replace content validation for unknown content.

---

# 184. Content Disarm and Reconstruction

CDR MAY be used for high-risk document types by:

```text
parsing safe content
removing active elements
reconstructing normalized output
```

---

# 185. CDR Suitability

Potential candidates include:

```text
PDF
DOCX
XLSX
PPTX
```

depending on product and tooling.

---

# 186. CDR Tradeoff

CDR can alter document features.

# 400. Canonical File & Media Standard

The organizational standard is:

> **File and media handling is implemented as a security-sensitive ingestion pipeline rather than a raw byte-transfer feature. Every upload begins with an authorized intent that defines the owning actor/resource/tenant, acceptable file classes, size/resource constraints, destination, and lifetime. Clients may upload directly to object storage for efficiency, but direct upload never bypasses trusted server-side authorization, finalization, content validation, security processing, or lifecycle governance.**

> **Uploaded content is untrusted regardless of filename, extension, MIME header, storage provider, or transport source. Supported file types are explicitly allowlisted and verified using an appropriate combination of extension parsing, canonical MIME detection, file signatures, format-aware parsing, decoding, rewriting, or transcoding. Complex document, archive, image, audio, and video formats additionally enforce decoded/expanded resource limits so compressed or malformed files cannot create unbounded CPU, memory, disk, or parser load.**

> **Uploaded data is stored under application-generated opaque identities in private object storage by default. Original filenames are retained only as untrusted display metadata, sensitive information is avoided in object keys, and the application maintains an authoritative file record containing ownership, tenant scope, storage identity, canonical type, size, state, retention class, and processing status. Pending files remain in quarantine until all required validation, malware scanning, content disarm, moderation, or transformation controls have reached an accepted state.**

> **Private retrieval always re-establishes authorization. The application validates the caller against the file or owning domain resource before streaming content or issuing a short-lived scoped signed URL. Signed URLs are treated as bearer capabilities, restricted to the minimum object, operation, and useful lifetime, and excluded from ordinary logging and analytics. Public sharing, revocation, expiry, and access auditing are modeled as product capabilities rather than implemented solely through effectively permanent signed object URLs.**

> **File delivery is safe by construction. Accepted objects are served using trusted canonical content types, appropriate download dispositions, browser anti-sniffing controls, and—where active or attacker-controlled content is rendered—origin isolation and restrictive browser policy. Public and cached derivatives use immutable/versioned identities where practical. Private thumbnails, previews, video segments, OCR text, extracted text, and other derived assets inherit the source file's tenant, authorization, residency, retention, and deletion boundaries unless an explicit authorized publication transition changes them.**

> **Media and document processing occurs through bounded, least-privileged worker pipelines. Images enforce decoded-pixel constraints and are normalized/rewritten before typical public delivery; videos/audio are probed and transcoded into supported output profiles where appropriate; archives enforce expansion, nesting, count, and path protections; and complex parsers operate with restricted filesystem, network, identity, CPU, memory, and execution-time capabilities proportional to risk. Files that deterministically crash or fail parsers become quarantined poison inputs rather than infinite retries.**

> **Malware and content-safety controls are risk-based but fail safely. File classes whose threat model requires antivirus, sandboxing, or content disarm remain unavailable until those checks succeed. Scanner timeout or unavailability is not equivalent to a clean result. Sensitive customer files are not submitted to third-party public scanning systems without explicit privacy, vendor, and data-processing approval, and malicious detections produce controlled security events rather than ordinary processing failures.**

> **Metadata is deliberately governed. Public derivatives remove unnecessary EXIF, GPS, document-author, hidden-history, embedded-thumbnail, and other sensitive metadata unless product behavior requires it; orientation and essential rendering semantics are preserved during normalization. Extracted metadata and OCR are treated as untrusted derived data and are subject to the same privacy, authorization, residency, retention, and search-governance controls as their source file.**

> **File lifecycle extends beyond upload. Every file class defines retention, expiry, legal-hold behavior, backup/recovery classification, version handling, and deletion semantics. Temporary upload intents, abandoned multipart sessions, processing intermediates, and generated exports expire automatically. Deletion removes or expires the authoritative source and all required derivatives, search projections, share records, caches/CDN copies, and obsolete storage versions according to privacy and recovery policy, while immutable backups follow the organization's approved deletion-replay and backup-retention controls.**

> **File/media infrastructure is observable and testable. Systems measure upload throughput and failures, validation rejection, scanner health, quarantine backlog, processing latency, transformation failure, storage growth, retention cleanup, and private-download behavior as appropriate. Security testing includes MIME/extension spoofing, hostile filenames, traversal, malformed formats, archive/pixel bombs, active content, signed-URL scope and expiry, scanner failure, cross-tenant retrieval, derived-asset leakage, metadata exposure, and complete deletion.**
