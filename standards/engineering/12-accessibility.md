# Accessibility Guidelines — Gold Standard 2026

## 1. Purpose

These guidelines define the canonical accessibility standard for all product interfaces.

They apply to:

- web applications;
- public websites;
- internal applications;
- admin systems;
- mobile-responsive web interfaces;
- forms;
- navigation;
- dialogs;
- menus;
- tables;
- charts;
- dashboards;
- data visualizations;
- realtime interfaces;
- media;
- documents generated by the product;
- design-system components.

The organizational baseline is:

```text
WCAG 2.2
Level AA
```

unless a stronger contractual, regulatory, customer, or jurisdiction-specific requirement applies.

The core principle is:

> **Accessibility is a correctness requirement of the product, not an optional visual enhancement.**

---

# 2. Normative Language

- **MUST** — mandatory.
- **MUST NOT** — prohibited.
- **SHOULD** — expected unless a documented reason exists.
- **SHOULD NOT** — generally avoided unless justified.
- **MAY** — optional.

Accessibility exceptions SHOULD document:

```text
Affected functionality
Barrier
User impact
WCAG criterion where applicable
Reason
Compensating alternative
Owner
Remediation plan
Review date
```

---

# 3. Compliance Floor

All user-facing interfaces MUST target:

```text
WCAG 2.2 AA
```

as the minimum organizational accessibility baseline.

AAA criteria MAY inform internal best practices even where full AAA conformance is not required.

---

# 4. Compliance Is Not the Goal by Itself

A technically conforming interface can still be difficult to use.

Teams SHOULD optimize for:

```text
Perceivable
Operable
Understandable
Robust
+
Actually usable
```

rather than checklist completion alone.

---

# 5. Accessibility Is Cross-Functional

Accessibility responsibility spans:

```text
Design
Engineering
Content
QA
Product
Documentation
```

It is not delegated solely to accessibility specialists.

---

# 6. Accessibility by Default

The design system SHOULD make accessible implementation the path of least resistance.

A developer using canonical components correctly should receive:

```text
semantics
keyboard support
focus behavior
accessible states
contrast-aware tokens
```

without rebuilding these concerns feature by feature.

---

# 7. Native HTML First

Prefer native semantic HTML before ARIA.

Examples:

```html
<button>
<a>
<input>
<select>
<textarea>
<table>
<dialog>
<nav>
<main>
```

are generally preferable to recreating equivalent behavior with generic elements.

---

# 8. The First Rule of ARIA

If native HTML already provides the required semantics and interaction:

> **Use the native element.**

Do not add ARIA simply because an interface is "accessible."

---

# 9. ARIA Does Not Add Behavior

ARIA can describe semantics.

ARIA does not automatically provide:

```text
keyboard behavior
focus management
selection logic
interaction
```

Custom widgets require implementation of those behaviors.

---

# 10. Accessibility Tree

Interfaces MUST expose meaningful:

```text
role
name
state
value
relationships
```

to accessibility APIs where relevant.

---

# 11. Semantic Structure

HTML structure SHOULD communicate document meaning independently of visual styling.

Examples:

```text
heading
paragraph
list
navigation
article
table
form
button
```

should remain identifiable programmatically.

---

# 12. Visual Appearance Is Not Semantics

A styled `<div>` that visually resembles a button is still not a button.

Likewise:

```text
bold text
```

is not automatically a heading.

Use semantic elements.

---

# 13. DOM Order

DOM order SHOULD reflect:

```text
reading order
focus order
logical workflow
```

Visual CSS rearrangement MUST NOT create a misleading sequence.

---

# 14. Landmarks

Major application regions SHOULD use appropriate landmarks.

Typical page structure:

```text
header
nav
main
aside where applicable
footer
```

---

# 15. Main Landmark

Each page SHOULD normally contain one primary:

```html
<main>
```

representing its main content.

---

# 16. Multiple Navigation Regions

If multiple navigation landmarks exist, give them distinguishing accessible names.

Example:

```text
Primary navigation
Project navigation
Footer navigation
```

---

# 17. Skip Link

Pages with repeated navigation SHOULD provide a keyboard-accessible mechanism to bypass it.

Common pattern:

```text
Skip to main content
```

---

# 18. Skip Link Visibility

Skip links MAY remain visually hidden until focused.

They MUST become clearly visible when keyboard focus reaches them.

---

# 19. Headings

Headings MUST represent meaningful content hierarchy.

Use:

```text
h1
h2
h3
...
```

according to structure, not desired font size.

---

# 20. Heading Levels

Avoid skipping levels merely for styling.

Preferred:

```text
h1
  h2
    h3
```

rather than:

```text
h1
  h4
```

without semantic reason.

---

# 21. Page Heading

Application pages SHOULD normally expose a clear programmatic page heading.

---

# 22. Heading Styling

Visual appearance and heading level are independent.

Use design tokens/classes to style semantic headings appropriately.

---

# 23. Lists

Use semantic lists when content represents a list.

```html
<ul>
<ol>
<li>
```

provides information that generic repeated `<div>` elements do not.

---

# 24. Description Lists

Use description lists when representing term/value relationships where appropriate.

---

# 25. Links

Use links for navigation.

Use buttons for actions.

---

# 26. Link vs Button

Canonical distinction:

```text
Navigate
→ Link

Perform action
→ Button
```

Do not choose based solely on visual appearance.

---

# 27. Link Destination

Link text SHOULD give meaningful destination context.

Prefer:

```text
View invoice
```

over repetitive:

```text
Click here
```

---

# 28. Duplicate Link Text

Repeated generic link labels MAY require contextual accessible names.

Example:

```text
View invoice INV-1042
```

for assistive technology.

---

# 29. New Window Behavior

Opening a new tab/window SHOULD be deliberate.

Avoid forcing new windows where ordinary navigation is sufficient.

Communicate unexpected context changes where necessary.

---

# 30. Buttons

Use native `<button>` elements for actions wherever possible.

---

# 31. Button Accessible Name

Every button MUST have an accessible name.

Icon-only buttons require an accessible name such as:

```text
Close
Delete project
Open navigation
```

---

# 32. Icon-Only Buttons

The icon's visual meaning is not sufficient by itself.

Provide a programmatically determinable name.

---

# 33. Button Text

Visible button labels SHOULD clearly describe actions.

Prefer:

```text
Save changes
Delete workspace
Send invitation
```

over:

```text
OK
Submit
Yes
```

when the action can be named explicitly.

---

# 34. Disabled Controls

Disabled controls SHOULD still leave users able to understand why an action is unavailable when that information is necessary.

Do not create inaccessible dead ends.

---

# 35. Disabled vs Hidden

Do not hide an unavailable action if users need to understand that it exists but cannot currently be used.

Choose deliberately.

---

# 36. Keyboard Accessibility

All functionality that can be operated with a pointer MUST also be operable through a keyboard where the function is not inherently pointer-specific.

---

# 37. Keyboard-Only Completion

A keyboard-only user MUST be able to complete all essential workflows.

This includes:

```text
navigation
forms
dialogs
menus
tables
file selection
settings
checkout
administration
```

---

# 38. Standard Keyboard Conventions

Custom controls SHOULD follow established platform/APG keyboard conventions.

Users should not need to learn arbitrary keys for ordinary widgets.

---

# 39. Tab

`Tab` and `Shift+Tab` SHOULD move between logical interactive components.

---

# 40. Composite Widgets

Within composite widgets such as:

```text
menu
tablist
radio group
tree
grid
```

arrow-key navigation MAY be appropriate instead of placing every child in the page Tab sequence.

Follow the canonical accessible pattern.

---

# 41. Enter

Enter SHOULD activate controls where expected.

Links and buttons should retain native behavior.

---

# 42. Space

Space SHOULD activate controls where native/platform conventions require it.

Do not remove expected keyboard behavior.

---

# 43. Escape

Escape SHOULD dismiss temporary interfaces where established conventions apply.

Examples:

```text
dialog
popover
menu
combobox popup
```

provided doing so does not cause data loss without appropriate handling.

---

# 44. Arrow Keys

Arrow-key navigation SHOULD follow standard interaction patterns for:

```text
radio groups
menus
tabs
listboxes
grids
sliders
```

---

# 45. Custom Keyboard Shortcuts

Custom keyboard shortcuts SHOULD be introduced sparingly.

They MUST avoid conflicts with:

```text
browser
OS
assistive technology
```

commands.

---

# 46. Shortcut Discoverability

Keyboard shortcuts SHOULD be discoverable if they are important to efficient operation.

---

# 47. Single-Character Shortcuts

Avoid single-character shortcuts that unexpectedly trigger when focus or speech-input context changes unless the applicable WCAG safeguards are implemented.

---

# 48. Keyboard Traps

Keyboard focus MUST NOT become trapped in a component unless trapping is intentional for a modal interaction and users can exit through an expected mechanism.

---

# 49. Focus Is State

Keyboard focus is application state with UX consequences.

Treat focus movement intentionally.

---

# 50. Visible Focus

Every keyboard-operable component MUST expose visible keyboard focus.

Never globally remove:

```css
outline: none;
```

without providing an equivalent or stronger indicator.

---

# 51. Focus Ring

The design system SHOULD provide one canonical focus-ring treatment.

It must remain visible against relevant backgrounds.

---

# 52. Focus Contrast

Author-created focus indication SHOULD achieve strong visible contrast against adjacent colors.

A minimum 3:1 contrast for the meaningful non-text indication is the baseline.

---

# 53. Focus Appearance

Although WCAG's detailed Focus Appearance criterion is AAA, the organizational design system SHOULD target a clearly visible focus indicator at least equivalent to a substantial perimeter/ring rather than a subtle color shift.

---

# 54. Focus and Hover

Focus appearance MUST NOT depend on hover.

Keyboard users may never trigger hover.

---

# 55. Focus and Selection

Do not confuse:

```text
focused
selected
active
```

states.

They can be different simultaneously.

---

# 56. Focus Not Obscured

When a component receives keyboard focus, author-created content MUST NOT completely hide it.

---

# 57. Sticky Headers

Sticky headers must not hide focused elements when users Tab or navigate anchors.

Use appropriate:

```text
scroll margin
layout
focus management
```

where necessary.

---

# 58. Sticky Footers

Sticky action bars MUST NOT obscure:

```text
focused controls
form errors
content
```

especially at high zoom.

---

# 59. Focus Order

Focus order MUST follow the meaningful workflow.

Avoid positive `tabindex` values as a mechanism to repair incorrect DOM structure.

---

# 60. tabindex

Preferred usage:

```text
tabindex="0"
→ include custom element in natural focus order when necessary

tabindex="-1"
→ programmatic focus target
```

Positive values SHOULD generally be avoided.

---

# 61. Programmatic Focus

Move focus programmatically only when a meaningful context change requires it.

---

# 62. Route Changes

Single-page applications SHOULD manage route-transition focus intentionally.

A user navigating to a new page should be able to understand that navigation occurred and begin at an appropriate point.

---

# 63. Page Navigation Focus

After client-side route navigation, a common strategy is to move focus to:

```text
page heading
main region
```

depending on product architecture.

---

# 64. Do Not Steal Focus

Background refreshes, toasts, and minor updates MUST NOT unexpectedly steal keyboard focus.

---

# 65. Focus Restoration

Temporary interfaces SHOULD restore focus to a logical location after closure.

Usually:

```text
trigger that opened the interface
```

unless the workflow created/removed something requiring a different destination.

---

# 66. Removed Focus Target

If the triggering element no longer exists after an operation, focus should move to a logical nearby target.

---

# 67. Semantic Controls

Prefer native controls because browsers provide established:

```text
keyboard behavior
focusability
state exposure
form behavior
```

automatically.

---

# 68. ARIA Roles

ARIA roles MUST match actual implemented behavior.

Do not write:

```html
<div role="button">
```

unless the element genuinely behaves like a button.

---

# 69. ARIA State

Dynamic state MUST be kept synchronized.

Examples:

```text
aria-expanded
aria-selected
aria-checked
aria-disabled
aria-pressed
```

must reflect actual UI state.

---

# 70. Invalid ARIA

Incorrect ARIA can create a worse experience than no ARIA.

Do not add roles/states without understanding their semantics.

---

# 71. Redundant ARIA

Avoid redundant roles on native elements unless a specific interoperability requirement justifies them.

---

# 72. Accessible Names

Every interactive component MUST have an appropriate accessible name.

Accessible naming SHOULD preferably derive from visible text where possible.

---

# 73. Visible Label Alignment

The accessible name SHOULD contain or closely correspond to visible label wording.

This supports speech-input users as well as screen-reader users.

---

# 74. aria-label

Use `aria-label` when an appropriate visible label cannot reasonably provide the accessible name.

Do not use it to replace useful visible text.

---

# 75. aria-labelledby

Use `aria-labelledby` where an existing visible element provides the appropriate name.

---

# 76. Accessible Description

Additional help/context MAY use:

```text
aria-describedby
```

or the equivalent relationship.

Descriptions should supplement names, not replace them.

---

# 77. Hidden Text

Visually hidden text MAY provide additional accessible context.

It must remain available to assistive technologies.

---

# 78. Hidden Content

Content intentionally hidden from everyone should generally not remain exposed to accessibility APIs.

---

# 79. aria-hidden

Never place:

```text
aria-hidden="true"
```

on a focusable element or an ancestor containing active focusable controls.

---

# 80. Decorative Icons

Purely decorative icons SHOULD be hidden from the accessibility tree.

Their adjacent text provides meaning.

---

# 81. Functional Icons

Icons conveying functionality without visible text need accessible naming.

---

# 82. Status Icons

Do not communicate:

```text
success
warning
error
status
```

through an icon or color alone.

Provide text or another equivalent cue.

---

# 83. Images

Meaningful images require appropriate text alternatives.

---

# 84. Informative Images

Alt text SHOULD communicate the information or function relevant to the surrounding context.

Do not mechanically describe every visual detail.

---

# 85. Decorative Images

Decorative images SHOULD use an empty text alternative where appropriate.

They should not create screen-reader noise.

---

# 86. Functional Images

If an image acts as a control, its accessible name should communicate the action rather than merely describe the image.

---

# 87. Complex Images

Complex diagrams, charts, and infographics may require:

```text
short text alternative
+
longer textual explanation/data representation
```

---

# 88. Images of Text

Avoid images containing text when normal text can provide the same presentation.

Text must remain selectable, resizable, translatable, and adaptable.

---

# 89. Contrast Baseline

Normal text MUST meet at least:

```text
4.5 : 1
```

contrast against its background.

---

# 90. Large Text Contrast

Large text MAY use the WCAG AA minimum:

```text
3 : 1
```

according to WCAG's large-text definition.

---

# 91. Avoid Threshold Design

Do not intentionally design every color combination exactly on the minimum ratio.

Rendering, anti-aliasing, themes, and displays vary.

Maintain practical margin.

---

# 92. Non-Text Contrast

Meaningful visual information required to identify:

```text
controls
states
graphical objects
focus
```

MUST meet the applicable 3:1 contrast requirement against adjacent colors.

---

# 93. Input Borders

If a visible border is required to identify an input, that border must have sufficient non-text contrast.

---

# 94. Placeholder Contrast

Placeholder text SHOULD remain readable.

It MUST NOT be the only label.

---

# 95. Disabled Contrast

WCAG contrast rules contain exceptions for inactive controls, but disabled states SHOULD still remain understandable and not disappear into the interface.

---

# 96. Color Is Not Enough

Color MUST NOT be the only means of conveying information.

Bad:

```text
green = passed
red = failed
```

without another indication.

---

# 97. Status Encoding

Use combinations such as:

```text
color
+
icon
+
text
```

for critical status.

---

# 98. Links Within Text

Inline links MUST be identifiable without relying only on color unless the applicable contrast and state behavior satisfy the accessibility requirement.

Underlines are usually the clearest convention.

---

# 99. Error States

Form errors require textual indication.

A red border alone is insufficient.

---

# 100. Required Fields

Required state must not rely only on color or an unexplained symbol.

---

# 101. Charts and Color

Chart series MUST remain distinguishable without color perception alone.

Possible distinctions:

```text
line style
marker shape
labels
pattern
direct annotation
```

---

# 102. Dark Mode

Dark mode MUST meet the same accessibility requirements as light mode.

It is not exempt because it is optional.

---

# 103. High Contrast

Interfaces SHOULD remain usable with operating-system/browser high-contrast or forced-colors modes where supported.

---

# 104. Forced Colors

Do not remove essential borders/icons/state indicators merely because custom CSS colors disappear in forced-color environments.

---

# 105. User Styles

Avoid author styles that unnecessarily prevent users from applying their own:

```text
font sizes
colors
spacing
zoom
```

---

# 106. Zoom

Interfaces MUST remain usable at increased browser zoom.

---

# 107. Text Resize

Text MUST remain usable when resized to:

```text
200%
```

without loss of content or functionality.

---

# 108. Reflow

At the equivalent of:

```text
320 CSS px
```

for vertically scrolling content, users MUST NOT generally need two-dimensional scrolling to read or operate content.

Exceptions exist where two-dimensional layout is genuinely essential.

---

# 109. 400% Zoom Test

A practical desktop test SHOULD include:

```text
1280 px viewport
+
400% browser zoom
```

which approximates the WCAG 320-CSS-pixel reflow condition.

---

# 110. Horizontal Scrolling

Ordinary:

```text
text
forms
settings
cards
navigation
```

should not require horizontal scrolling at narrow/reflowed widths.

---

# 111. Legitimate Two-Dimensional Content

Some content may genuinely require horizontal and vertical navigation.

Examples:

```text
large data table
map
diagram
canvas
timeline
```

Contain the scrolling to that region where practical.

---

# 112. Fixed Heights

Avoid fixed-height text containers that clip content when:

```text
zoom
translation
user font settings
```

increase text size.

---

# 113. Text Truncation

Do not truncate information required to complete a task without a way to access the full value.

---

# 114. Ellipsis

If ellipsis is used, users SHOULD have an accessible method to obtain complete content when it matters.

---

# 115. Responsive Accessibility

Responsive layout changes MUST preserve:

```text
content
functionality
semantics
focus order
```

not merely visual appearance.

---

# 116. Mobile Recomposition

Desktop multi-column interfaces SHOULD recompose into readable mobile structures rather than shrink unusably.

---

# 117. Orientation

Do not lock content to one device orientation unless orientation is essential to functionality.

---

# 118. Touch Targets

WCAG 2.2 AA minimum pointer-target sizing MUST be satisfied.

The baseline target is:

```text
24 × 24 CSS px
```

subject to WCAG-defined exceptions.

---

# 119. Preferred Touch Target

For ordinary product controls, the internal design-system target SHOULD generally be larger than the WCAG minimum.

Preferred target for important touch actions:

```text
≈ 44 × 44 CSS px
```

where layout permits.

---

# 120. Small Icons

A 16 px icon MAY sit inside a larger interactive hit area.

Visual size and target size are different concepts.

---

# 121. Target Spacing

Closely packed small controls increase accidental activation.

Use adequate spacing, especially for:

```text
delete
close
pagination
table row actions
```

---

# 122. Destructive Touch Targets

Destructive actions SHOULD NOT be placed immediately beside common primary actions with tiny separation.

---

# 123. Pointer Gestures

Functionality requiring complex pointer gestures SHOULD have a simpler single-pointer alternative unless the gesture is essential.

---

# 124. Drag and Drop

Drag-and-drop MUST NOT be the only way to perform an essential operation.

Provide alternatives such as:

```text
Move up/down
Select destination
File picker
```

---

# 125. Motion

Motion SHOULD support understanding rather than decoration alone.

---

# 126. Reduced Motion

The application MUST honor:

```css
prefers-reduced-motion
```

for nonessential motion as an organizational standard.

This requirement intentionally goes beyond relying only on the minimum AA set.

---

# 127. Reduced-Motion Behavior

When reduced motion is requested, remove or substantially reduce:

```text
large translations
parallax
zoom effects
continuous movement
decorative animation
```

that is not essential.

---

# 128. Essential Motion

If movement communicates necessary information, provide a reduced alternative that preserves meaning.

---

# 129. Opacity Transitions

Simple low-impact opacity transitions may remain appropriate under reduced-motion mode if they do not cause motion-related harm.

Use judgment.

---

# 130. Auto-Playing Motion

Avoid automatically playing distracting movement.

Users SHOULD be able to pause, stop, or hide moving content where applicable.

---

# 131. Continuous Animation

Decorative continuous animation SHOULD stop under reduced-motion preferences.

---

# 132. Parallax

Parallax SHOULD be disabled under reduced motion.

---

# 133. Scroll-Linked Motion

Avoid large scroll-linked transformations as essential navigation.

---

# 134. Flashing Content

Content MUST NOT flash in ways that create seizure risk.

Do not produce content exceeding applicable WCAG flash thresholds.

---

# 135. Animation Timing

Do not make functionality dependent on users completing actions during brief animation windows.

---

# 136. Time Limits

Avoid time limits unless necessary.

Where time limits exist, provide applicable:

```text
warning
extension
adjustment
```

mechanisms.

---

# 137. Session Timeout

Users SHOULD receive advance warning before session expiry when unsaved work or interruption is likely.

---

# 138. Authentication Timeout

Security session timeouts remain legitimate.

Accessibility requires making the process understandable and recoverable without weakening security.

---

# 139. Auto-Advancing Content

Carousels/slides SHOULD NOT auto-advance in a way users cannot control.

---

# 140. Pause Controls

Moving/auto-updating content requiring user attention SHOULD expose suitable pause/stop controls.

---

# 141. Screen Readers

Interfaces MUST expose sufficient semantics for screen-reader users to understand:

```text
structure
controls
states
relationships
updates
```

---

# 142. Screen Reader ≠ Linear Visual Description

Do not attempt to narrate every visual detail.

Expose semantic meaning.

---

# 143. Source Order

Screen readers generally consume semantic DOM order.

CSS positioning MUST NOT produce a contradictory reading sequence.

---

# 144. Name, Role, Value

Interactive components MUST expose appropriate:

```text
name
role
value/state
```

to assistive technology.

---

# 145. Dynamic Updates

Important dynamic content changes SHOULD be communicated appropriately when they occur without moving focus.

---

# 146. Live Regions

Use live regions for status information that users need to hear without navigating to it.

---

# 147. aria-live

Choose:

```text
polite
assertive
```

according to urgency.

Most product updates should use `polite`.

---

# 148. Assertive Announcements

Reserve assertive announcements for urgent information.

Overuse can interrupt screen-reader users repeatedly.

---

# 149. Do Not Announce Everything

Frequent data updates SHOULD NOT all become live announcements.

This creates unusable noise.

---

# 150. Status Messages

Examples appropriate for accessible status messaging:

```text
Changes saved
3 results found
Upload completed
Connection lost
```

---

# 151. Loading Announcements

Long-running transitions MAY communicate:

```text
Loading…
```

where the loading state is not otherwise apparent.

Do not announce tiny background requests.

---

# 152. Error Announcements

Submission errors SHOULD become discoverable to screen-reader users.

Use:

```text
focus management
error summary
associated field messages
live status
```

appropriately.

---

# 153. Notifications

Toasts MUST NOT require visual observation alone.

Important notifications should be exposed to assistive technologies.

---

# 154. Toast Timing

Do not disappear critical messages before users can perceive or interact with them.

---

# 155. Interactive Toasts

If a toast contains:

```text
Undo
Retry
View
```

the control must be keyboard accessible.

---

# 156. Forms

Forms MUST follow the Forms & Validation Gold Standard and WCAG 2.2 AA requirements.

---

# 157. Form Labels

Every user-input control MUST have an accessible label.

---

# 158. Visible Form Labels

Visible persistent labels SHOULD be used for ordinary form fields.

Placeholder-only fields are prohibited.

---

# 159. Label Association

Labels must be programmatically associated with controls.

Use:

```html
<label for>
```

or equivalent native/design-system relationships.

---

# 160. Grouped Controls

Related controls such as radio/checkbox groups SHOULD use:

```html
<fieldset>
<legend>
```

where appropriate.

---

# 161. Form Instructions

Required formats or important instructions SHOULD be provided before users encounter predictable errors.

---

# 162. Required Status

Required fields need accessible and visible indication.

---

# 163. Autocomplete

Use recognized autocomplete attributes where appropriate.

This particularly helps users with:

```text
motor
cognitive
memory
```

limitations.

---

# 164. Input Purpose

Common personal-data inputs SHOULD expose machine-determinable purpose where applicable.

---

# 165. Form Errors

Automatically detected errors MUST identify the affected item and describe the error in text.

---

# 166. Error Recovery

Errors SHOULD explain how to fix the issue.

Prefer:

```text
Enter an email address in the format name@example.com.
```

over:

```text
Invalid value.
```

---

# 167. Error Summary

Long forms SHOULD consider an accessible error summary.

---

# 168. Error Summary Links

Error summaries MAY link users directly to problematic controls.

---

# 169. Error Focus

After failed submission, focus SHOULD move to:

```text
error summary
```

or the first invalid control according to the established pattern.

---

# 170. Error Preservation

Do not erase valid entered data after validation failure.

---

# 171. Color and Forms

Error/success/required states cannot rely solely on:

```text
red
green
yellow
```

color.

---

# 172. Form Descriptions

Help text and error text should be programmatically associated with controls.

---

# 173. Disabled Submit

Avoid permanently disabled submit controls that provide no explanation for users who cannot determine why submission is unavailable.

---

# 174. Pending Submission

Pending form state should be perceivable to:

```text
visual
keyboard
screen-reader
```

users where meaningful.

---

# 175. Accessible Authentication

Authentication must support:

```text
password managers
paste
autocomplete
passkeys
keyboard
zoom
```

where applicable.

---

# 176. CAPTCHA

```text
keyboard entry
```

# 180. Dialogs

Modal dialogs MUST follow an established accessible dialog pattern.

# 181. Dialog Role

Modal dialog containers require appropriate dialog semantics.

# 182. Dialog Name

Every dialog MUST have an accessible name.

# 185. Initial Focus — Simple Dialog

For a simple confirm dialog, focus may move to the first appropriate interactive control.

---

# 187. Dialog Focus Containment

While a modal dialog is active:

```text

```

must not move into inert background content.

---

# 188. Background Inertness

Users must not be able to interact with content behind a modal dialog.

---

# 189. Dialog Escape

Escape SHOULD close ordinary modal dialogs unless doing so would create an unsafe or ambiguous operation.

---

# 190. Dialog Close Control

Dialogs SHOULD contain a visible keyboard-operable method for closing/cancelling.

---

# 191. Dialog Focus Restoration

On close, return focus to:

```text
trigger
```

or another logical target when the workflow changed the page.

# 192. Confirmation Dialogs

Destructive dialogs must state:

```text
resource
consequence
reversibility
```

rather than only:

```text
Are you sure?
```

---

# 193. Alert Dialog

Use alert-dialog semantics only for urgent modal information that truly requires immediate attention.

Do not use alert dialogs for ordinary notifications.

---

# 194. Popovers

Nonmodal popovers require intentional:

```text
focus
dismissal
keyboard
trigger state
```

behavior.

# 195. Disclosure

The trigger should expose:

```text
aria-expanded
```

where applicable.

# 196. Menus

Do not use ARIA menus for ordinary site navigation solely because it visually resembles a menu.

# 197. Navigation Menus

# 198. Menu Keyboard Model

True ARIA menus require expected arrow-key interaction and focus management.

```text
relationships
```

```text
name
```

# 244. Keyboard Charts

# 246. SVG Charts

# 247. Canvas

Canvas content requires an accessible alternative if it contains required information or functionality.

# 248. Maps

# 249. Data Visualization Interaction

# 259. Error States

Repeated components/navigation SHOULD behave and be identified consistently.

# 298. Reading Width

# 300. Line Height

---

# 301. Paragraph Spacing

Use consistent spacing between paragraphs and sections.

---

# 302. All Caps

Use capitalization according to content rather than visual emphasis alone.

---

# 303. Decorative Fonts

Decorative typography SHOULD NOT reduce readability of primary content.

# 304. Icons + Labels

# 305. Responsive Text

---

# 306. Fixed Font Sizes

# 308. Sticky UI at Zoom

# 311. Pointer Hover

# 312. Hover and Focus Parity

# 453. Golden Accessibility Rules

**1. WCAG 2.2 AA is the minimum organizational baseline.**

**2. Accessibility is product correctness.**

**3. Native HTML comes before ARIA.**

**4. ARIA describes behavior; it does not implement behavior.**

**5. Every interactive control has an accessible name.**

**6. Links navigate; buttons perform actions.**

**7. Every essential operation works with a keyboard.**

**8. Keyboard focus is always visible.**

**9. Focus order follows logical reading/workflow order.**

**10. Focus must not be hidden behind author-created content.**

**11. Temporary interfaces manage focus deliberately.**

**12. Modal dialogs contain focus and make the background inert.**

**13. Closing temporary UI restores focus logically.**

**14. Color is never the sole carrier of meaning.**

**15. Normal text meets at least 4.5:1 contrast.**

**16. Large text meets at least 3:1 contrast.**

**17. Meaningful controls/graphics meet applicable 3:1 non-text contrast.**

**18. Text remains usable at 200% resizing.**

**19. Ordinary content reflows at the WCAG 320-CSS-pixel condition.**

**20. Pointer targets satisfy WCAG 2.2 AA minimum sizing/spacing.**

**21. Important touch targets should generally be larger than the compliance minimum.**

**22. `prefers-reduced-motion` is honored for nonessential motion.**

**23. Essential information never depends on hover alone.**

**24. Dragging has an alternative where it is not inherently essential.**

**25. Forms have visible labels and accessible errors.**

**26. Validation errors identify the field and explain recovery.**

**27. Tables use real table semantics when representing tabular data.**

**28. Interactive grids are used only when grid behavior is genuinely required.**

**29. Charts provide meaning beyond visual color and geometry.**

**30. Important charts have accessible summaries/data alternatives.**

**31. Dynamic status changes are communicated intentionally.**

**32. Screen-reader users should not receive unnecessary announcement noise.**

**33. Mobile/responsive variants preserve semantics and focus order.**

**34. Dark mode meets the same accessibility standard as light mode.**

**35. Third-party widgets are part of the product accessibility surface.**

**36. Automated accessibility testing is required but insufficient.**

**37. Manual keyboard testing is mandatory for meaningful interaction.**

**38. Critical complex workflows receive representative screen-reader testing.**

**39. Accessibility regressions are product defects.**

**40. Accessibility is reviewed throughout design, implementation, testing, and maintenance—not at the end.**

# 454. Canonical Accessibility Standard

The organizational standard is:

> **All product interfaces target WCAG 2.2 Level AA as the minimum accessibility baseline. Interfaces use semantic HTML and native interaction whenever practical, with WAI-ARIA applied only where native semantics cannot express the required widget or state. Every interactive element exposes an appropriate accessible name, role, state, and value; all essential functionality is keyboard operable; focus is visible, logically ordered, and intentionally managed across navigation, dialogs, overlays, and dynamic workflows.**

> **Visual design satisfies minimum text and non-text contrast requirements, never relies solely on color, supports text enlargement and reflow, and provides appropriately sized and spaced pointer targets. Product interfaces remain usable under browser zoom, narrow layouts, localization, high-contrast environments, and reduced-motion preferences. Nonessential motion is reduced or removed when users request reduced motion.**

> **Forms provide visible labels, instructions, programmatically associated errors, recoverable validation, and accessible submission states. Modal dialogs follow established focus and keyboard patterns. Data tables preserve row/column relationships, while charts and visualizations provide accessible summaries, non-color distinctions, sufficient contrast, and data alternatives where exact information is required. Dynamic status updates are exposed intentionally without overwhelming assistive-technology users.**

> **Accessibility is built primarily into canonical design-system components and verified at multiple levels through static analysis, automated accessibility tests, keyboard testing, zoom/reflow checks, contrast verification, reduced-motion checks, and representative screen-reader testing. Automated tools supplement rather than replace human evaluation. Accessibility defects are treated as product defects and receive durable regression protection where practical.**

A production-grade accessible interface should make it easy to answer:

```text
What is the semantic structure?
What does a screen reader perceive?
Can every essential action be completed without a mouse?
Where does focus go?
Can I always see focus?
What happens to focus after this dialog closes?
Does the interface still work at 200% text size?
Does it reflow at high zoom?
Is important meaning conveyed without color?
Do text and controls have sufficient contrast?
Are pointer targets large enough?
What happens with reduced motion enabled?
Are all fields labelled?
How are errors announced?
Can a user operate this table without losing row/column context?
What does a nonvisual user get from this chart?
Do loading and status changes get communicated?
Does mobile preserve the same semantics?
Has this been tested beyond an automated scanner?
```

If those questions cannot be answered, the interface is not yet accessibility-ready.

A few exact standards distinctions matter. WCAG 2.2 AA requires **24×24 CSS-pixel pointer targets or qualifying spacing/other exceptions**; 44×44 is therefore used above as the stronger internal ergonomic target, not misrepresented as the AA minimum. citeturn959311search2 Similarly, WCAG 2.2 AA requires a **visible** focus indicator and that focused controls are not entirely hidden by author-created content, while the more prescriptive focus-indicator area requirement belongs to the AAA Focus Appearance criterion. citeturn959311search0turn119886search7turn959311search4

For complex widgets, W3C's current ARIA Authoring Practices explicitly notes that custom ARIA GUI components do **not** receive keyboard behavior automatically; developers must implement the appropriate keyboard model. Its modal-dialog pattern, for example, requires focus to move inside the dialog, keeps `Tab`/`Shift+Tab` within the modal, and normally uses `Escape` to close it. citeturn464441search6turn464441search4 For tables, W3C continues to recommend native HTML tables whenever practical because their structural relationships can be exposed directly to assistive technologies. citeturn119886search8turn464441search9
